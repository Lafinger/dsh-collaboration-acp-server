# 07 问题澄清与风险处理

[返回需求总览](README.md)

## 目的

持续跟踪拒收、信息缺口与风险，明确由谁处理、如何确认，避免把已回答、已分析或已发布新版当作问题解决。

## 核心需求

| 编号 | 需求 |
| --- | --- |
| ISSUE-001 | 持续问题应记录事实、来源、相关任务与成果版本，以及必须确认解决的角色；跨方案、评估和任务版本保留同一问题及历史。 |
| ISSUE-002 | 下游拒收应关联问题和上游审核待办，保存原标准、被拒成果版本与原因；新版提醒不能覆盖拒收事项。 |
| ISSUE-003 | 上游可提出整改、说明无需修改或请求澄清。整改进入方案审核；无需修改的说明仍须交回相关下游核对。 |
| ISSUE-004 | 澄清应分别保存问题、回答和相关角色对回答是否充分的决定；允许暂时无法回答或继续补充，不覆盖旧回答。 |
| ISSUE-005 | 同一问题应累计记录重评次数与用量，不因重试、拆合方案或任务升版清零。业务重评达到上限后转人工澄清；必要确认齐全后，按规则续开一次额度并保留累计记录。 |
| ISSUE-006 | 问题解决须由全部必需确认角色基于固定处理结果分别确认；方案生效、整改完成或澄清充分不自动关闭问题。 |
| ISSUE-007 | 严重风险应记录来源版本、条件及证据，追踪已接收该版本的任务，以及实际使用该输入或经复核沿用的后续成果。 |
| ISSUE-008 | 受影响对象应有风险处理待办，可确认修正版已采用且处理完成、证明不受影响、确认已批准终止用途且实际影响已消除，或转入澄清；转入澄清仍保留风险。 |
| ISSUE-009 | 未处理的严重风险应阻止受影响任务完成和继续交接，并说明原因；允许保存进展及接收合格修正版，保留修复路径。 |
| ISSUE-010 | 业务信息不足与模型、传输、用量或文件故障应分别提示；技术失败不能伪装成业务澄清，也不表示问题解决。 |
| ISSUE-011 | 以终止用途处理风险时，应提供已批准的范围变化、停止使用及影响消除的证据，由相关角色负责人确认；保留原缺陷与历史，不将该结果描述为缺陷修复。 |

## 关键规则

- 澄清充分、问题解决和风险处理是不同决定，不能互相替代。每个必需角色由其负责人确认；未反馈不视为同意。
- 澄清及异议的确认责任由现任负责人承接，交接不代表回答充分或事项解决；按[人员交接规则](01-项目与角色管理.md)办理。遗漏审核角色的异议按[方案审核](04-项目推进与方案审核.md)处理，项目管理不能代替提异议角色确认。
- 重新分析不能漏掉原问题的必需确认角色；可增加有依据的相关角色。分析次数和用量控制见[Agent 分析](03-Agent分析与上下文.md)，技术额度不足不自动续额，也不制造业务问题。
- 新版发布不自动解除风险。应逐项核对采用情况、整改结果、不受影响或用途终止后的影响消除证据；尚未产生成果但已接收问题版本的任务也在影响范围内。
- 内部取消任务或归档意向不能证明实际影响消除。成果已对外交付或仍被使用时，须核实后续使用与影响；证据不足继续保留风险，不能仅凭内部取消结案。
- 不撤回成果或撤销接收。已完成任务保留原完成事实，展示后续风险，通过[任务升版](06-需求变化与任务整改.md)整改。
- 普通待接收、待反馈不是异常；不得通过超时自动批准、关闭问题或解除风险。

## 验收要点

- **ISSUE-001～003**：拒收可追到上游处理；无需修改的说明回到下游核对；新版不能吞掉原问题。
- **ISSUE-004～005**：无法回答或回答不充分不关闭缺口、不续开额度；必要确认齐全后重复提交也只续开一次，累计记录保留。
- **ISSUE-006**：任一必需角色未确认，问题仍未解决；模型成功和任务完成均不能绕过确认。
- **ISSUE-007～009**：跨多层引用及尚未产生成果的任务均能查到风险；澄清不解除风险，修正版可以接收并进入处理。
- **ISSUE-010**：信息不足、模型失败和文件损坏分别给出原因与处理入口，不要求成员用业务决定掩盖技术故障。
- **ISSUE-011**：批准终止用途后仍需相关负责人核对实际影响消除的证据；对外交付或仍在使用不能仅凭内部取消结案，结果不记为缺陷修复。交接只转移确认责任，不自动解决原澄清或异议。

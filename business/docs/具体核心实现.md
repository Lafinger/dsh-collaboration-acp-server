## 一、技术架构

### 1.1 一句话

一个 DSH 插件，把项目的资料、方案、确认、任务和成果存进一个 SQLite 库，通过 ACP 接受调用；**无界面、无权限**。

### 1.2 分层

自上而下五层，**依赖只能向下**：

```
tool/        模型可调用的工具（薄：参数校验 + 调 service）
service/     业务规则与事务边界（厚：全部状态机在这里）
sqlite/      表结构、迁移、仓储（只做存取，不含业务判断）
domain/      类型、错误码、ID、不变量（无 I/O，可独立测试）
index.ts     插件装配：注入 tools、打开库、注册工具
```

**为什么这样分**：`DSH-taskboard` 的实测数据表明，复杂度**必然**集中在 `service` + `sqlite`（它 1687 行的 provider 占了整个代码库的大头）。分层的作用不是"好看"，而是让**业务规则可被单独测试**——不让 SQL 和状态机缠在一起，否则"方案生效要单事务"这种要求根本无法验证。

**关键纪律**：`domain/` 不许 import 任何 I/O；`sqlite/` 不许做业务判断（不判断"该不该生效"，只负责存）。违反这两条，事务边界就会失控。

### 1.3 插件装配（`index.ts`）

```ts
import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'project-workbench'

export interface Config {
  readonly databasePath: string
  readonly fileRoot: string
}

export const Config: z<Config> = z.object({
  databasePath: z.string().default('.dsh/workbench.sqlite'),
  fileRoot: z.string().default('.dsh/workbench-files'),
})

export function apply(ctx: Context, config: Config): void {
  const db = openDatabase(config.databasePath)
  ctx.effect(() => () => db.close())        // 保证库被关闭
  ctx.inject(['tools'], (toolCtx) => registerTools(toolCtx, services))
}
```

（`z` 是 `@deepseek-ai/schemastery` 的**默认导出**，注意写法。）

**必须用 `defineTool()` 包装工具，并声明 `output`**——裸对象会被静默丢弃。这是实测踩过的坑，细节见验证清单第六节。

### 1.4 数据流

```
ACP 会话 → 模型调用工具 → tool/ 校验参数
                              ↓
                         service/ 做决定（含事务）
                              ↓
                         sqlite/ 读写
                              ↓
                         返回结果 → 模型 → 用户
```

**没有别的写入路径**。这是"SQLite 是唯一权威"的落实方式。

### 1.5 错误处理

统一用 `domain/error.ts` 的 `WorkbenchError(code, message, details)`。工具层捕获后转成**模型能理解的说明**，而不是抛栈——模型看不懂栈，但看得懂"必需输入未接收，任务 X 还不能提交"。

## 二、核心模块实现

### 2.0 模块划分与依赖顺序

实现顺序应**沿数据流**，不要按需求编号顺序：

```
1. domain/      类型与不变量           ← 无依赖，先做        ✅ 已完成
2. sqlite/      建表 + 迁移 + 仓储      ← 依赖 domain        ✅ 已完成
3. service/项目与角色（M1）             ← 第一个可跑通的纵切   ✅ 已完成
4. service/资料与版本（M2）             ← 已实现            ✅ 已完成
5. service/分析（M3）                   ← 已实现            ✅ 已完成
6. service/方案 + 确认门禁（M4）        ← 已实现            ✅ 已完成
7. service/任务与任务版本（M5 身份层）  ← 已实现            ✅ 已完成
8. service/进展、成果与接收（M5 成果层）← 已实现            ✅ 已完成
9. service/待办与通知（M6）             ← 已实现            ✅ 已完成
10. service/追溯（M7）                  ← 已实现            ✅ 已完成
11. 端到端演练（MVP-032）                ← 两段全过          ✅ 已完成
```

### 2.1 角色与成员（M1）

角色是**九个固定槽位**，不是可创建的对象。每个槽位一个成员字符串，可为空。

```
角色槽位：项目管理 | 产品 | 设计 | 场景模型 | 场景美术 | 数据 | 前端 | 后端 | UE端
每个槽位：member（可变字符串，可为空）
```

**三条不变量**（务必写进代码断言）：

1. 一个角色最多一名成员
2. 成员可随时改，**不产生任何交接或审批记录**
3. 每条业务记录保存**当时的成员快照**，而非外键引用

第 3 条最关键：如果记录只存 `role_id` 并靠 join 取当前成员，改成员后历史就会被"追溯篡改"——这与 MVP-031 直接冲突。**快照必须冗余存在记录上。**

### 2.2 方案与确认门禁（M4，MVP 的核心）

这是 MVP 唯一的关键机制，也是唯一需要真正事务的地方。

**数据结构**：一份方案有多个**版本**；每个版本有若干**确认槽位**（一个相关角色一个）。

```
方案 v1 ──┬── 槽位(产品)   → 同意
          ├── 槽位(设计)   → 未反馈
          └── 槽位(前端)   → 同意
```

**门禁规则**：全部槽位**同意**才能生效；任一未反馈或拒绝即不生效。

**确认记录只增不改**：方案修订后，旧确认**保留并标记失效**，记录作废原因与时间。不物理删除——否则"产品曾同意过 v1"这个复盘时最有价值的事实会消失。

**角色空缺**：该角色无成员时，槽位存在但显示"角色空缺"，方案**停在等待**，不自动通过、不代确认。

### 2.3 核心事务：方案生效（`applyPlan`）

**这是整个 MVP 最需要小心的 40 行代码。**

一次生效要同时完成 5 件事：

1. 写方案状态为已生效
2. 写正式计划
3. 创建全部任务
4. 建立任务间的输入依赖
5. 关闭已完成的确认槽位

**必须在单事务内完成**，否则会出现"任务建了一半、待办没关"的半生效状态——这是最难排查的故障形态。

```
BEGIN IMMEDIATE                    ← 立刻取写锁，避免升级锁竞态
  重新校验：全部槽位已同意？       ← 校验必须在事务内
  重新校验：依赖无环、无悬空引用？
  写入上述 5 项
COMMIT
```

**两个要点**：

- **用 `BEGIN IMMEDIATE` 而非 `BEGIN`**：后者先取读锁、写入时再升级，并发下可能失败重来。已实测本机 `node:sqlite` 支持。
- **校验放在事务内**：否则"校验通过"与"写入生效"之间有窗口，可能基于过期状态生效。

**幂等**：重复提交同一次生效不应产生重复任务（对应保留的 `OPS-007`）。可在方案上加"已生效"标记并在事务内先检查。

### 2.4 依赖成环检测

必需输入指向"上游成果版本"，因此天然是一张有向图。**Agent 生成的方案可能包含环**，若不拦截，两个任务会永远无法开始。

**在方案登记时（MVP-017）就检测并拒绝**，不要等任务执行时才发现——此时尚未收确认，拒绝代价最小。

实现：建图后做拓扑排序，或对每个节点做 DFS 找后向边。**环的具体链路要回给模型**，否则它不知道该改哪里。

### 2.5 任务与成果（M5）

**版本模型是双序列**，这点容易写错：

- **任务版本**：任务定义变化（如经新方案整改）产生
- **成果版本**：每次提交产生

**两者独立编号，但成果版本必须记录"产生时的任务版本号"**。否则整改后无法回答"当时要求是什么"，而这是 MVP-031 的硬要求。

**状态推进的三个"不等于"**（必须写成显式检查，不能靠约定）：

| 动作 | 不产生什么 |
| --- | --- |
| 保存进展 | 不完成、不驱动下游 |
| 提交成果 | 不完成（只产生待确认版本） |
| 上游完成 | 不等于下游已接收 |

**提交的前置校验**：必需输入指向的成果版本**已被本任务接收**。校验不通过就拒绝并说明是哪一条输入没接收。

**成果版本不可变**：整改靠**新版本**，不修改旧版本。

### 2.6 待办与通知（M6）

**待办归属角色，不归属"所有人"**。一条待办 = "某个角色需要就某个对象做某个决定"。

**已读按角色槽位记录**，不按人——因为没有成员体系，"alice 已读"与"bob 已读"在数据上无法区分。

**待办 ≠ 通知**：

- 待办：需要**反馈**（方案确认、成果确认、成果接收）
- 通知：纯**告知**

**阅读不产生任何业务决定**，已交付的待办不因读取而消失，只能通过提交对应决定来关闭。

### 2.7 追溯（M7）

追溯 = **能沿着"输入 → 方案 → 任务 → 成果 → 决定"这条链走通，并区分当时的版本与当前版本**。

实现要点是**冗余而非 join**：每条决定记录当时依据的版本号、成员快照、时间、理由。这样即使上游资料已更新到 v5，仍能还原"当时是基于 v2 做的决定"。

**历史只读**：对旧版本的操作用新版本进行，不改写历史。

### 2.8 工具集切分

按**读 / 写 / 决定**三种语义切，约 12–15 个工具：

| 类别 | 例 | 特点 |
| --- | --- | --- |
| 读 | 查项目、查资料、查任务、走追溯 | 无副作用，可放心让模型调 |
| 写 | 建项目、传资料、存进展、提成果 | 有副作用，但不产生正式决定 |
| **决定** | 登记方案、确认、接收、拒收 | **产生正式事实**，命名要让模型一眼识别 |

**为什么按语义切**：模型需要能一眼分辨"这一步会不会产生正式决定"。命名混乱会导致误调——而误调一个"确认"是不可撤销的。

**工具名用动词开头、语义明确**，如 `plan_register`、`confirm_submit`、`result_accept`。

### 2.9 资料与固定版本（M2）——已实现

M2 是数据流上第一个"有内容"的模块，也是两条硬性要求的落地处。

#### 三个概念，别混

| 概念 | 是什么 | 变了会怎样 |
| --- | --- | --- |
| **资料**（material） | 一份具名的输入。身份 = 项目 + 原文件名 + 用途 | 不会变——它是版本的容器 |
| **资料版本**（version） | 一次上传形成的**不可变**内容 | **永不修改**。更新 = 追加 |
| **固定引用**（reference） | `(资料ID, 版本号)` | 永远解析到同一版本，**不回退到最新版** |

**关键设计**：**用途参与身份**。同名文件但用途不同 → 是**两份资料**，各自从 v1 开始。这样"这份是需求说明、那份是参考资料"不会互相覆盖，而"同一份需求说明改了两版"才形成 v1/v2。

#### 上传流程（`MaterialService.upload`）

```
校验项目可写 → 校验参数 → 读源文件 → 算 sha256
   ↓
BEGIN IMMEDIATE
  （新资料才）INSERT materials
  next = MAX(version) + 1          ← 不是 COUNT
  mkdir + 复制文件到 <项目>/<角色>/materials/<资料ID>/v<n>__<原名>
  INSERT material_versions（含相对路径）
COMMIT
   ↓
失败则删除已复制的文件（不让事务回滚留下孤儿文件）
```

**顺序很重要**：**先读源文件，再动库**。源文件不存在时立刻返回，因此不可能留下半写状态。

#### 两条硬性要求怎么落地的

**一、取号在事务内、用 `MAX+1`**

```ts
const next = this.materials.latestVersion(materialId) + 1
```

不是 `COUNT(*)+1`。两者**只在版本无缺口时相同**——删掉中间一版后，`COUNT` 会**重复发放已存在的号**，生成同名文件从而覆盖。

再加一条 `UNIQUE (material_id, version)` 与 `UNIQUE (rel_path)` 作为兜底：即使取号逻辑将来被改错，重复也会在写入时被拒并整体回滚。

**二、输出路径必须约束在 `fileRoot` 内**

外部输入（项目 key、角色、文件名）**全部**经 `FileRoot.resolve()`，且 `assertSafeSegment` 逐段拒绝 `..`、分隔符、盘符。

> **校验必须在写入之前**。`path.relative` 遇到越界**不报错**（静默返回 `..\..\` 开头的路径），所以"写完再检查相对路径"等于没检查。

**两道防线，各自被单独测试**：`assertSafeSegment` 拦非法段，`contains()` 拦越界。**第一道会先命中，所以第二道在普通测试里永远走不到**——我把它抽成 `contains()` 单独测，否则它可以被删掉而测试全绿（这真的发生过，见下）。

#### 命名与不便之处

**原文件名原样保留**（含空格、括号、中文）。实测 `v1__设计稿 v1 (最终版).txt` 工作正常——这正是"用 ID 做目录、原名只做显示名"的价值：若用原名做目录，这个路径早就出问题了。

#### 这一段踩到的坑

**坑一：我写的测试假设错了，代码是对的。**
我断言"传入绝对路径的 `originalName` 应被拒绝"。实际 `versionFileName` 会把分隔符替换成 `_`，所以它塌缩成**一个安全段**，上传成功但落在 `fileRoot` 内。**代码行为正确**（调用方的绝对路径不该左右写入位置），错的是测试。已改为断言"写入确实落在根内"。

**坑二：变异测试暴露了两处空转断言。**

| 变异 | 修之前 | 修之后 |
| --- | --- | --- |
| 关掉 `contains()` 越界检查 | 全绿 ❌ | **1 红** ✅ |
| `MAX+1` 改成 `COUNT+1` | 全绿 ❌ | **1 红** ✅ |

两处都是**测试没测到该测的东西**：前者因为第一道防线先命中，后者因为版本无缺口时两种算法结果相同。补的方法是：把 `contains()` 抽出来单独测；构造**有缺口的版本序列**让两种算法分道扬镳。

> **教训**：断言写得再多，也可能全是空转。**只对关键防线做变异测试**（这里两条），就能发现"测试通过但守不住"的情况。

### 2.10 分析与建议（M3）——已实现

M3 的难点不在"让模型分析资料"，而在**MVP-013 的可核对性**。若做法是"给模型一份清单、让它自己调 `material_read`"，那么"只读范围内的资料"**无法验证**——它手里有通用工具，没有任何东西阻止它读范围外的东西。

**所以范围是工具的输入，不是对模型的请求。**

#### 两步式：只读入参，不读自述

```
analysis_begin(project_id, trigger, scope=[{material_id, version}, ...])
   ↓ 服务端按 scope 逐个读出内容（含哈希）
   ↓ 返回：内容 + 读不到的（含原因）
analysis_submit(project_id, trigger, scope, requirements[], undecided[], inferences[], ...)
   ↓ 服务端【重新读一遍】scope，用它自己看到的结果落库
```

**关键**：`submit` **不接受**调用方关于"读了什么"的说法，而是**自己再读一次**。这样"实际读取范围"是**系统的事实**，不是模型的宣称。

副作用是好的：范围外的内容**从未进入上下文**，所以"不读范围外"不需要任何自觉。

#### 两类未覆盖：客观的归系统，主观的归模型

| 类别 | 谁记录 | 例子 |
| --- | --- | --- |
| **客观** | **系统**（模型无法省略） | 版本不存在、文件从磁盘上消失、超过大小上限 |
| **主观** | 模型 | "这段看不懂"、"缺少某依据" |

**为什么必须分开**：客观事实**不该由被考核方自己汇报**。否则会出现一种很隐蔽的失败——模型读了 3 份、其中 1 份失败，却交出一份看起来完整的分析。服务端强制并入后，那条失败**必然**出现在结果里。

这条在冒烟里被实测过：调用方声称未覆盖为空，文件其实已从磁盘删除 → `uncovered` 里仍然出现了 `unreadable`。

#### 三类内容靠参数分开，不靠自觉

`requirements` / `undecided` / `inferences` 是**三个独立参数**，不是"一个数组 + kind 标签"。这样"必须区分"是**契约**，模型想混也混不了——填 `requirements` 时它必须做一次显式归类。

**明确需求必须带来源**，且来源**必须落在本次 scope 内**：

```
requirements: [{ text: "必须支持离线", sources: [{material_id, version}] }]
```

**理由**：一条自称"明确需求"的内容，若指不出哪一版资料支持它，**它与推断没有区别**。范围外的来源等于**伪造依据**，服务端当场拒绝（`SOURCE_OUT_OF_SCOPE`，冒烟实测）。

#### 两个刻意的"不做"

**不做"进行中的分析"。** `analysis_begin` **不落库**，只有 `submit` 才产生记录。中途放弃的分析**不留痕**。记录"进行中"会立刻引出"超时怎么办、要不要清理、如何显示"，而这些**没有需求支持**。

**不做截断。** 超过上限（256 KB）的文件**不读**，记入未覆盖。**静默截断是谎言**——模型拿到半份内容却以为完整，会基于半份材料下结论。承认"没读到"远比假装读过诚实。

#### 这一段踩到的坑

**坑一：`items` 必须内联，不能提取成常量。**

我先把 scope 的 item schema 抽成 `const SCOPE_ITEMS`，结果**19 个类型错误**：`execute` 收到的 `args.scope` 退化成 `JsonValue`。

原因：参数类型推断读的是**声明处的字面量形状**。提到 `const` 之后 `type` 被拓宽成 `string`、`required` 拓宽成 `boolean`，**item 类型就丢了**。

修法：在每个使用点**内联写出**。已加注释警告"不要 DRY 这个"。

**坑二：四个守卫全部做了变异测试。**

| 变异 | 结果 |
| --- | --- |
| 关掉 scope 来源校验 | **3 红** ✅ |
| 丢掉服务端发现的客观未覆盖 | **2 红** ✅ |
| 超限改为截断 | **3 红** ✅ |
| 允许来源为空 | **1 红** ✅ |

其中第一个变异**第一次没跑起来**——编译器先报了 `TS6133: 'scopeIndex' is declared but never read`。我把它改成 `&& false` 保留使用，才真正跑到测试。**这提醒我：变异必须确认真的编译通过并执行了**，否则"没红"会被误读成"守住了"。

**坑三：测试临时目录在失败时泄漏。**

清理写在 `cleanup()` 里手动调用，而**断言失败会抛过它**——一次失败留下一堆 `wb-m3-*`。我是在一次失败运行后才发现 `%TEMP%` 里躺着 9 个目录。

修法：`harness.ts` 里注册**进程退出钩子**统一清理。已实测：**故意让断言失败，泄漏数仍为 0**。失败时才是清理最该生效的时候，而原来的写法恰好在那里失效。

**坑四：ACP 冒烟起不来，问题不在插件。**

新建的 profile **没有输出任何东西**（连 `initialize` 都不回）。查下来是我用 `dsh plugin add` 建 profile 时**只加了 `dsh-base` 和我的插件**，**漏掉了 `@deepseek-ai/dsh-acp-app`**——没有它就没有 ACP 入口。

修法：用 `--from-default-profile acp` 重建。**教训**：把"插件装好了"当成"入口也在"是错的，两者是**独立的 bundle**。

### 2.11 方案与确认门禁（M4）——已实现

**MVP 唯一的门禁**。一句话规则：**每个相关角色都同意，才生效；在此之前什么都不发生。**

#### 状态是算出来的，不是存出来的

`gate`（门禁状态）**不落库**，每次由确认槽位推导：

| 状态 | 含义 |
| --- | --- |
| `waiting` | 还有人没表态 —— 分列 `pending` / `vacancies`（角色空缺）/ `rejected` |
| `unanimous` | 全部同意 |
| `superseded` | **被修订取代**，本版确认已全部作废 |

**为什么不存**：存了就会和证据分离。算出来的状态**不可能与槽位不一致**。

**`rejected` 单独列出**，不混进 `pending`：「没人看」和「有人反对」是**两件事**，调用方需要能区分。

#### 四条硬规则怎么落地的

**一、确认属于角色，不属于人。** 一个人占两个角色，**必须提交两次**：

```
confirm(product, Zhang) → waiting   ← 只有 product 的槽位被填
confirm(design,  Zhang) → unanimous
```

若一次提交能顶多个角色，「全部相关角色同意」就被架空了。测试里专门造了"同一人占满所有角色"的场景。

**二、角色空缺就等，不放行、不代签。** 空缺意味着**没人能行动**，所以它单列在 `vacancies` 里。注意：空缺角色**仍可被确认**（补人后确认即可）——真正的保证是**别人的同意不能算它的**。

**三、生效必须在单事务内。** 实测方式：把 `plan_activations` 表删掉，逼最后一步失败，然后检查——**设计的确认也回滚了**，`activated_at` 全为 null。**没有半生效。**

**四、修订是追加，作废是标记。** 修订产生**新版本**，旧确认**标记失效而非删除**，作废原因记录在**每一条**上。`plan_history` 保留全部版本。

> **允许在收齐前修订**（MVP-021）。禁止会让人卡在"收齐前不敢动"，反而更糟。代价是已收到的确认全部作废。

#### 一个非显然的安全性质

`plan_confirm` **只作用于最新版本**。传入旧版本号没有意义——因为确认的目标是"这份方案的当前版本"，而**被取代的版本永远不会再累积确认**。冒烟里实测过：修订后再次确认，**落在 v2**，v1 的槽位保持作废。

#### 依赖成环在登记时就拒绝

**此时尚未收任何确认，代价最小**（MVP-017）。错误信息**点名环**（`a -> b -> a`）而不只是说"有环"——后者不可操作。菱形依赖**不是环**，有专门测试。

#### 事务嵌套：savepoint

**SQLite 没有嵌套 `BEGIN`。** 而 M4 需要组合事务操作（如"登记修订 + 作废旧确认"）。原来的 `inTransaction` 直接 `BEGIN IMMEDIATE`，嵌套调用会抛错。

改成**按连接记录深度**：外层 `BEGIN`，内层 `SAVEPOINT`，内层失败 `ROLLBACK TO` 而**不影响外层**。已测：内层失败后，**外层的写入仍在**。

> **不能**偷懒让内层"跳过事务"——那会在最需要原子性的地方悄悄破坏原子性。

#### 这一段踩到的坑

**坑一：主键设计错了，第 2 版根本存不进去。**

我写的注释是"内容存在带版本的行里"，但主键只写了 `id`：

```sql
id TEXT PRIMARY KEY,   -- 错：一个 id 只能有一行
version INTEGER NOT NULL,
```

结果**任何修订都失败**（`UNIQUE constraint failed: plans.id`），4 个测试红。

**注释写对了，实现写错了** —— 这种不一致最难发现，因为它"看起来"是深思熟虑过的。改成 `PRIMARY KEY (id, version)`，子表外键一并指向 `(id, version)`。

**坑二：SQL 注释里的反引号截断了模板字符串。**

我在 `MIGRATION_4` 的注释里写了 `` `id` ``，而整个迁移是**模板字符串**——反引号直接把它闭合了，`tsc` 报 4 个语法错。改成不加反引号。

**坑三：我写错了一个测试的前提。**

我断言"未配置成员的角色**不能被确认**"（期待 `ROLE_NOT_RELEVANT`）。实际它**可以**——空缺角色补人后当然要能确认，那正是正常流程。

真正的保证是"**别人的同意不算它的**"。已改成断言：product 同意后，design 槽位**仍为 null**、方案**仍未生效**。

**坑四（最有价值）：冒烟"通过"了，但模型读输出时发现了一处不一致。**

`plan_history` 里 v1 的 `gate` 显示 `waiting: pending: [product, design]` —— 好像**从来没人表过态**。而实际上它有过一次同意、一次拒绝。

原因：`gateStateOf` **过滤掉已作废的槽位**，所以被取代的版本重算出来就是"全员待表态"。

**这抹掉了 `plan_history` 存在的意义。** 加了 `superseded` 状态并补了回归测试。

**教训**：这个 bug **不会让任何测试变红**——它输出的是**结构正确、语义错误**的数据。**只有真正读一遍输出**才能发现。变异测试和断言都帮不上忙。

### 2.12 任务与任务版本（M5 身份层）——已实现

**这一层只做一件事：让任务存在。** 不做进展、不做成果、不做完成。任务建出来**只能看，不能被推进**——这是刻意的中间状态。

#### 两个标识符，不能互换

| 标识符 | 作用域 | 用途 |
| --- | --- | --- |
| `ref` | **一份方案版本内** | 让依赖能指向**同一份方案里、尚未创建的任务** |
| `task_id` | **全局、跨版本稳定** | 任务的身份 |

`add` 用 `ref`（此刻还没有身份），`modify` / `cancel` 用 `task_id`。**两套并存是必然的**，不是缺陷。

**把配对写错是最容易犯的错**，所以两个方向都在**登记时**显式拒绝：

- `add` 带了 `task_id` → `ADD_MUST_NOT_NAME_A_TASK`
- `modify`/`cancel` 没带 → `TASK_TARGET_REQUIRED`

#### 生效的六个步骤（ADR-0009）

```
1. 校验：add 的 ref 唯一；目标存在、未完成、未取消
2. 建所有 add            → 得到 ref → task_id 映射
3. 用映射解析依赖         → 连同内容写入该任务版本
4. 处理 modify           → 各自产生新版本
5. 处理 cancel           → 标记终止
6. 写账本 plan_task_outcomes
```

**全部在单个事务内。** 任一步失败整体回滚。

**为什么必须两遍**：一个方案里可以有 `t2 depends_on t1`，而**两个都是新增的**。一遍处理时 `t1` 的身份还没生成。**这不是优化，是语义要求**（有专门测试）。

#### 两处校验，代价要说清

登记时校验让错误**在尚未收确认时**暴露；生效时**再**校验，因为**状态会在收确认的窗口里变**：登记时某任务未完成，收确认期间它可能完成了。

不做第二次校验，"修改已完成任务"就会通过，**ADR-0008 的冻结保证被破坏**。

**代价**：方案可能在**收齐确认后仍然失败**。这看似很糟，但比悄悄改掉一个已完成任务好得多。失败是原子的，方案停在待生效，可以 `plan_revise` 重来。

> 这是本层最反直觉的设计点，也是唯一一处"成功路径会失败"的地方。有四个测试专门盯它，包括"失败后仍可修订并成功生效"。

#### 取消与完成是两种终结

两者都**冻结定义**，都不删除任何东西。但它们是**不同的状态**（`cancelled_at` / `completed_at`），任务**可以未完成而被取消**。

冻结的理由相同：**旧成果记录着它产生时的任务版本，改掉那一版会让"当时要求是什么"失真**。要恢复就**新建任务**，不是取消冻结。

#### 依赖成环之外，取消也要看下游

`cancel` 一个**被下游依赖**的任务 → 登记时拒绝（`TASK_HAS_DEPENDENTS`），与成环同理：**此时尚未收确认，代价最小**。**不做级联取消**——调用方提案 3 个任务、系统悄悄取消 7 个，**没人看得见**。

#### 那一个依赖既不是 ref 也不是任务

依赖可以指向**本次新增的任务**（用 ref），也可以指向**已存在的任务**（用 task_id）——后者是项目进行中的常态。M4 原本只允许前者，**这一层把它改成两者都行**，并且**跨项目依赖被拒绝**。

#### 这一段踩到的四个坑

**坑一：M4 的依赖校验和 M5 直接矛盾。**

M4 的 `validateDraft` 要求 `depends_on` **必须是本方案内的 ref**。而 ADR-0009 说依赖**可以指向已存在的任务**。写完测试立刻撞上：`task "a2" depends on "...", which is not in this plan`。

**这是两个模块对同一字段的理解不一致**，而且**只有把两层接起来跑才会暴露**。修法是让 `validateDraft` 接受"ref 或已存在任务"，并把项目归属一并校验。

**坑二：`assert.throws` 不返回异常。**

我写了 13 处 `assert.throws(...) as unknown as WorkbenchError`，然后读 `.code`。**`assert.throws` 没有返回值**，所以每一处 `.code` 都是 `undefined`，13 个测试全红。

**教训**：这个写法**看起来完全合理**，TypeScript 也被 `as` 骗过去了。**类型断言在这里掩盖了运行时事实**。改成自己捕获的 `throwsWorkbench()`。

**坑三（最该记的）：我用正则批改测试文件，越改越坏。**

为了修坑二，我写了 codemod 脚本。第一版**括号配对算错一位**（从 `assert.throws(` 的第 14 个字符开始数，正好落在内层 `(` 上），匹配到空串。修好后又**吞掉了换行**，接着我用第二个正则去补换行，**却误伤了 `env()` 里的正常 `))` 序列**。

三轮下来文件彻底坏了，最后**推倒重写**才干净。

**教训**：**结构化的代码不要用正则改。** 每次"修一下"都引入了新的、更难发现的破坏，而且我**误以为脚本没输出就是没生效**。当时正确做法是**立刻停手重写**，而不是再写第四个脚本。

**坑四：测试假设了列表顺序。**

`listByProject` 按 `created_at` 排序，而**同一次生效创建的任务时间戳完全相同**，所以顺序**没有保证**。我用 `ids[0]` 当成"任务 a"，测试**时红时绿**。

改成**按角色查找**。这类 bug 最恶劣的地方是**它可能碰巧通过**。

| 单元测试 | **156 个**（M5 新增 29 个） |

| ACP 冒烟 | 登记 0 任务 → 生效 1 任务 → 修改出新版本 → 取消保留全部版本 |

**变异测试逐项**：

| 取消改成删除 | **3 红** |

**唯一存活的变异是诚实结论，不是漏测**：登记时**已经**拒绝重复目标，所以生效时那份检查**通过公开接口不可达**。我写探针**证实**了这一点，而不是猜。

代码保留了它，并注明原因：**这个函数正是"会把一个任务写两版"的地方，它不该依赖别处更早做过的检查来避免这件事。**

> 变异测试同样给过我教训：**第一版"不查重复"变异编译失败**（`refToTask` 变成未使用），报成 `DID NOT COMPILE`。**如果我不看这一列，就会误以为测试覆盖了它。** 每个变异都必须**真的编译并运行**，结论才有意义。

### 2.13 进展、成果与接收（M5 成果层）——已实现

**这一层最重要的一句话：提交不是完成。**

```
进展    → 只是记录，什么也不推进
提交成果 → 产生一个不可变成果版本 + 一个待审槽位
审核    → 唯一能写 completed_at 的地方
接收    → 下游各自的独立决定
```

#### 一条时间线，四件事不会互相冒充

```
progress_add  → completed_at 仍为空
result_submit → completed_at 仍为空   ← 最容易写错的地方
review:return → completed_at 仍为空，且不产生完成记录
review:complete → completed_at 有值   ← 只有这里
accept        → 与 completed_at 无关
```

**如果让"提交"顺手完成任务**，那 MVP-025 和 MVP-026 就是同一件事，**"确认"这个角色就没有存在意义了**。所以有专门的测试和变异测试盯这一条。

#### 进展挂在任务版本上

```
progress 有 task_version 字段
```

因为**整改前后是两份不同的要求**。若进展挂在任务上，"v1 按老要求做的"和"v2 按新要求做的"会混在一起。这条和 ADR-0008 保存任务版本、ADR-0010 成果记版本号，是**同一个理由的第三次应用**。

#### 退回保留成果版本

退回**不产生完成记录**（MVP-026），但**不丢弃成果**。被退回的那一版**正是整改的依据** —— 删了它，"上次到底哪里不行"就查不到了。

#### 只给声明过的下游开接收槽位

```
depends_on 建立的是"输入关系" → 由此开接收槽位
未声明该任务为输入的下游 → 没有槽位，也无法决定
```

**否则每个任务完成都会惊动全项目**，而大多数下游根本不消费它的产出。

> 冒烟测试里模型先**误判**了这一点（说 `depends_on` 不算声明），随后**自己纠正**了 —— 它观察到槽位确实开给了那个下游。这说明**边界是从行为推断的，不是从措辞**。

#### 拒收什么也不产生

MVP-027 明文：拒收产生**一条记录 + 一条通知**。

**最诱人的错误实现是"拒收就自动建一个整改任务"** —— 那是 MVP-016 禁止的自动创建任务，而且会让"拒收"变成一个**无人审阅的写操作**。所以有测试专门断言：拒收后**任务数、成果数都不变，且上游的完成状态不受影响**。

要整改，**上游自己走方案流程**（这正好接回 L198 的"新方案 → 多角色确认 → 新任务版本"）。

#### 必交成果只是文字

`required_results` 和 `completion_criteria` 存在**任务版本**上（它们是定义的一部分，改了就该产生新版本），都是**自由文本，系统不逐条校验**。

原因见 ADR-0010：**要逐条校验就必须回答"哪个文件对应哪个条目"**，那是匹配问题，而 MVP 明确不做质量判断。所以"完整性"在 MVP 里**只能意味着"交了东西"**。**这是诚实的边界，不是没做完。**

#### 一次提交 = 一个版本

说明、文件、自检**三样一起构成一个成果版本**。分开交会让"这一版该交的都在不在"无法判断 —— 而完整性校验的前提正是它们属于同一版。

文件本身落在 M2 的存储里，成果版本只记**引用 + 哈希**。

#### 这一段踩到的坑

**坑一：我又用正则批量改了源码文件。**

为了去掉几处冗余的 `ok: true`，我写了个 `-replace "(?m)^\s+ok: true,\r?\n"`。它**匹配了我以为的范围之外的东西**，我**又是靠猜**去推断删掉了什么，浪费了几轮。

**同一个教训在同一个会话里出现了第二次**（M5 身份层那次是测试文件，这次是源码）。正确做法始终是**用 edit 工具做定点替换**，或者**直接重写文件**。

**坑二：`required: false` 不是"可选"的写法。**

我按常识写了 `required: false`，结果**整个参数对象报错**：`Type 'false' is not assignable to type 'true'`。

原因是**类型从第一个声明处推断**，而**项目里所有现存工具都用"省略 `required`"表示可选**。我**发明了一个没人用过的写法**。

**教训**：新文件的写法要**先看同目录的邻居**，而不是凭记忆造。

**坑三：数组元素的对象结构不能随便写。**

`items: { type: 'object', properties: {...} }` 类型推断失败，必须**内联 `additionalProperties: false`**，与 `plan-tools.ts` 里已有的任务数组**逐字一致**。

这和更早记录的"**参数类型推断读声明处的字面量形状**"是同一条规则的第若干次出现。

**变异测试逐项**（这一层全是"禁止做某事"的规则，所以每条变异都针对一个**诱人的错误实现**）：

>
> 补了一个"a 喂给 b，c 无关"的用例才抓住。**这是夹具太单薄导致的漏网，不是代码问题。**

### 2.14 待办与通知（M6）——已实现

**这一层的核心决定：待办不落表。**

| 对象 | 存不存 | 原因 |
| --- | --- | --- |
| 待办 | **推导** | 三个来源的槽位已在库里是权威 |
| 通知 | **推导** | 同上 |
| **已读** | **落表** | **推导不出来**——没有别处记录"谁看过" |

#### 推导的理由只有一个：不可能不一致

三个来源各有稳定身份：

```
方案确认 → confirmations        (plan_id, plan_version, role)
成果确认 → result_confirmations (result_id, version)
成果接收 → acceptances          (result_id, version, task_id)
```

**另存一张待办表会立刻产生同步问题**：槽位被修订作废了，那张待办谁来删？**这个问题在 MVP 里没有便宜的解法**，而推导**不可能不一致**。

**代价**：每次查询要聚合几张表。MVP 规模下不构成问题。

#### 已读的必要例外

已读**推导不出来**，所以必须落表。而且 MVP-030 规定它**按角色槽位记录**，不按人：

```
reads 主键 = (kind, object_id, version, role, task_id)
```

这与 MVP 全局一致：**确认属于角色，不属于人**。角色换人后，之前以该角色身份读过的**仍然算读过**。

**"重复读取不重复计数"是主键约束保证的**，不是靠计数逻辑——逻辑会漂移，约束不会。

#### 空缺角色不产生未读

```
未读 = 未决槽位数 − 已读的（且该角色有成员）
```

**角色空缺时余数为 0**，不需要额外写一条"没有未读"的记录。

> **这一条如果不做**，"未读"会显示成**一个空角色欠了多少事**，而那个角色根本没人能来处理。

#### 读待办不关闭待办

**只有提交对应决定才能关闭待办。** 读既不关闭它，也不改变任何业务状态。

**这是最容易写错的地方**：一个"标记已读即关闭"的实现看起来更"顺手"，但它会让**读取变成一个业务动作**，而 MVP-030 明确说已读**不代表**同意、完成、接收或解决。

#### 冒烟测试逼出来的一个真实缺口

**这不是我设计出来的，是模型发现后我去查证的。**

冒烟时模型报了一个它自己注意到的反常：`design` 角色**在 `project_roles` 里连一行都没有**，却**照样确认了方案、也做了成果接收** —— 只靠 `submitted_by` 记了个名字「Li」。

`grep` 证实：**没有任何地方校验确认者所属角色是否有成员**。

MVP-019 只说"角色空缺时方案**停在等待并提示**"，**没说要禁止该角色确认**。所以代码**不违背字面要求**，但**一旦谁都能替空缺角色确认，"空缺"就退化成纯展示**。

**已按"拒绝"处理**：三处决定入口都校验，没有成员则 `VACANT_ROLE_CANNOT_CONFIRM`。

**理由**：空缺**不是待补的手续**，它意味着**项目还没说这件事归谁**；既然没人担任，**就不存在"他的同意"可以记录**。

**加载冒烟确认它真的挡住了**：`design` 的 `outcome` 始终为 `null`，任务数 **0**，生效方案数 **0**。

#### 这一层的验证

> 下表是 **M6 完成当时**的快照（当时共 213 个单测）。全项目当前规模见 §2.0。

| 手段 | 结果 |
| --- | --- |
| 单元测试 | **213 个**（本层新增 32 个） |
| 变异测试 13 项 | **11 项被抓，2 项经探针证明不可达** |
| ACP 冒烟 | 10 步走通，独立读库核对一致 |

**两个存活变异是诚实结论**，我用探针各自证明了原因，并**把原因写成测试**（`invariants that no reachable state can violate`）：

| 存活变异 | 为什么不可达（已证实） |
| --- | --- |
| 把已生效方案的槽位也当待办 | `revise` 对已生效方案返回 `PLAN_ALREADY_ACTIVE`，所以未决槽位**不可能**与已生效方案共存 |
| 未读不加下限夹紧 | 已读**只对仍是待办的槽位计数**，所以 `read` **不可能**超过 `pending` |

**补上的漏洞**：探针同时发现 `markRead` **接受不存在的槽位并写入成功**——那行永远匹配不到任何查询，调用方却被告知成功。这是**探针发现的，不是测试发现的**。已改为 `NOTICE_NOT_FOUND`。

> **这次的教训**：变异测试报"SURVIVED"时，**要么是缺测试，要么是代码不可达**。**猜是不行的**——我两次都写了探针去构造那个状态，才敢下结论。

### 2.15 追溯（M7）——已实现

#### M7 动工前先发现两个真实缺口

**M7 的目标是回答"当时是谁、依据哪一版、做了什么决定"。** MVP-031 的验收要点写得更具体：

> 从成果能查到它**生成时实际采用的输入版本**。

**动工前我用探针查了一下，发现这句话当时答不出来。** 两个缺口都是**跑出来的**，不是读代码猜的：

**缺口 A：输入版本根本没被记下。**

```
task_version_deps 只有 → { task_id, version, depends_on_task_id, position }
result_versions 的列   → 没有一列指向输入
```

上游发了 v1、v2 两版，下游接收了 v1 —— **库里查不出"下游用的是哪版"**。

**缺口 B：确认完成完全不校验必需输入。** 最极端的情况：

```
b has 1 UNDECIDED acceptance slot(s) open
>>> b COMPLETED with its required input still undecided.
```

**下游连决定都没做，照样确认完成。** MVP-026 要求"确认前须校验必需输入已接收"。

#### 缺口 A 的修法：接收时钉住版本

**接收这个动作本身就隐含了"我用的是这一版"**，所以钉住它**不新增任何动作**。

否掉的方案：

- **登记方案时钉住**（MVP-023 的字面读法）。否掉：登记时上游成果**可能还不存在**，只能先写"上游任务"，生效时再解 —— **绕一圈还是回到接收时**。
- **提交时由执行人声明**。否掉：多一个必填参数，且**声明可能与接收决定矛盾**，那时以谁为准？**两个真相来源必然打架。**

**拒收也记版本**，这样"决定过但拒收"与"根本没决定"**可区分** —— 追溯需要这个区别。

#### 缺口 B 的修法：确认完成的门槛

**有这个门槛才可能做到"M7 承诺的追溯"。** 补上之后：

| 下游的决定 | 能否确认完成 | 为什么 |
| --- | --- | --- |
| 已接收 | **可以** | 输入已消费 |
| **已拒收** | **不可以** | **上游还没做完**，此时下游不该能完工 |
| 还没决定 | **不可以** | 输入尚未消费 |
| 无必需输入 | **可以** | MVP-023 原文："未被指定输入的任务可直接执行" |

> **拒收为什么也拦**：被拒收意味着**上游交付物下游不要**，所以**上游必须整改重交**。整改的正规途径是**走方案流程产生新版本**（ADR-0008）。
>
> **不会死锁**：要解开，要么下游改为接收，要么上游走方案修订重做。**两条路都不需要新机制。**
>
> **只有"确认完成"被拦**：退回（return）**永远允许** —— 那是下游的正当结论。

#### 缺口 B 为什么能活过 213 个测试

**因为测试缺的正是这个场景。** 我查过：**没有任何一个已有测试"确认完成一个声明了必需输入的任务"** —— 所有依赖测试都只走了接收那一侧。

**校验不存在，用例也不存在。** 两样一起缺，所以全绿。

> **这是本项目第三次遇到同一类问题**（变异存活、探针发现漏洞、这次）。**"测试全绿"从来不等于"逻辑正确"，只等于"已写的用例没被违反"。**

#### 追溯的形态：按对象查决定链

回答的是 MVP-031 那句"**依据哪个版本、由谁、何时、作出什么决定**"，所以以对象为入口。

**`trace` 一个工具，取对象**：调用方知道自己手上是什么，而**这句话对三种对象是同一个问题**。

**当前版本与历史版本严格分开**：

| | 含义 | 会不会被改写 |
| --- | --- | --- |
| `decisions` | 当前生效的决定 | 否 |
| `history` | 被取代但保留可查的 | 否 |

**"历史只读"是结构保证的**：改变只能**产生新版本**，旧记录**没有任何更新路径**。

#### 探针顺带证明的一条性质

冒烟里模型注意到 `trace` 的 `result_version` 行曾经**把确认折进了提交行**。我改成**两条独立记录**：

| 记录 | 回答 |
| --- | --- |
| `result_version` | **谁提交的**（提交者） |
| `result_review` | **谁判的、判成什么、为什么**（决定者） |

**折在一起会丢掉"已提交未审"与"已提交已判"的区别**，而退回**恰恰是带理由的决定**，必须独立可见。

#### 这一层的验证

| 手段 | 结果 |
| --- | --- |
| 单元测试 | **238 个**（本层新增 25 个） |
| 变异测试 11 项 | **9 项被抓，2 项经探针证明结构冗余** |
| 演练第一段（无模型） | **14 步全过**，每步独立复查 |
| 演练第二段（ACP） | **9 步走通**，读库核对 **15/15 链路完好** |
| 文件存储 | **两段的字节数 + sha256 都与库里一致** |

**两个存活变异是诚实结论**，各自用探针证明了结构性原因，**并把原因写成测试**：

| 存活变异 | 为什么不可达（已证实） |
| --- | --- |
| 无必需输入时也走门槛 | `required` 为空则 unmet 列表**必然为空**，空循环不产生任何拒绝 |
| 作废槽位被当成当前 | `revise` **只会写一个更新的版本**，所以作废槽位**永远在 latest 之下** |

**还修了一个测试自己的漏洞**：`result_version` 行的提交者变异曾存活，**因为我的测试提交和审查用了同一个名字**。改成两个名字后变异被抓。

### 2.16 归档是只读的，判据只留一份（审计修复）

**MVP-005 一句话覆盖四类写入**，而"是否可写"这个判断**原本散在各个 service 自己身上**。审计把每个写入口都跑了一遍：

| 写入口 | 归档后（修复前） |
| --- | --- |
| 上传资料 / 登记方案 / 改成员 | 被拒 |
| **记进展 / 提交成果 / 提交分析** | **写入成功** |

**归档后的项目还在继续收分析、收进展、收成果。**

> **探测本身踩过坑**：`analysis_submit` 第一次报 `SCOPE_REQUIRED`，**看着像已拦住**。实际是**我传了空 scope**，它在更早处就被拒。换合法 scope 才暴露真相。**探测方法错了，就会得到"一切正常"的假象。**

**根因不是有人写错，是同一个规则有五份副本** —— 漏的三处不是写错了，是**没人想起来要写**。

**决定：判据收进 `domain/project.ts` 的 `assertWritable`**，五个 service 一律转发。**"哪条路径忘了判断"从"读完五个文件"变成"搜一个函数名"。**

补的写入点：`analysis.submit`、`addProgress`、`submit`、`review`、`decide`、`openAcceptances`。**读不受影响** —— 需求说的是只读，不是消失。

**同一种病还出现在拒收通知上**：MVP-027 要求通知**上游主执行人**，而通知派生时 join 的是 `a.task_id`（**做决定的下游**）。实测上游 product/ANA、下游 design/BO 拒收 → 通知发给了 **design/BO**。**拒收人收到自己发的通知，被拒的人什么都不知道。** 改成 join `rv.task_id`（产出成果的那个任务）即可。

**两处纯投影缺口**（业务逻辑没错，只是没发出去）：

| 缺口 | 后果 |
| --- | --- |
| `task_get` 不返回必交成果与完成标准 | 执行人**看不到要交什么、什么算做完** |
| `project_get` 不返回当前正式计划 | 概览**缺了 MVP-003 点名的字段** |

**字段一直在库里，只是没有工具发出去。存了但拿不到，等于没有。**

**为什么能活过 213 个测试：测试只调 service，从不调工具。** 归档只测了资料与方案两条路径；`requiredResults` 只测了存储没测输出；拒收通知只测了存在性没测收件人。**被测的是"有没有这个东西"，没测"对不对、够不够"。**

**所以补了 `tool-output.test.ts`**，把"投影层"纳入被测范围。

### 2.17 文件存储

资料与成果的文件**不入库**，库里只存元数据；二进制内容放文件系统。

- **库**：结构化状态（唯一权威）
- **文件系统**：二进制内容

**为什么分离**：需求要处理三维资产与视频（`MAT-009`），大 BLOB 会让整库膨胀到 GB 级，拖慢备份与查询。`DSH-taskboard` 同样采用"库 + 附件目录"分离。

**代价**：失去"单一权威"的纯粹性——库与文件可能脱节（如有人手动删了文件）。用下面的哈希字段缓解。

#### 目录结构

```
<fileRoot>/<项目ID>/<角色>/materials/<资料ID>/v<版本号>__<原文件名>
<fileRoot>/<项目ID>/<角色>/results/<成果ID>/v<版本号>__<原文件名>
```

**根目录从配置读**，默认 `.dsh/workbench-files/`。

**四条命名纪律**：

1. **用内部 ID 做目录，不用原文件名**。原文件名可能重复、含 `/` 或 `:`、含中文与空格。把它**只当显示名**，路径就永远安全。（`MAT-001` 只要求"登记原文件名"，并未要求"按原名存储"。）
2. **版本号进文件名**，如 `v1__设计稿.png`。直接落实"更新是追加新版本"，肉眼可见，且写 `v2` 天然不覆盖 `v1`。
3. **按项目分目录**：归档或清理一个项目时可整目录处理，不必扫全库。
4. **按角色分目录**：见下。

#### 为什么在项目下再分角色

角色层让"谁的东西"在文件系统里直接可见——打开 `<项目ID>/产品/` 就是产品角色名下的全部资料与成果，与 MVP"各角色只关注自己的任务"的取向一致。

**归属规则**：

| 对象 | 归到哪个角色目录 | 依据 |
| --- | --- | --- |
| 资料 | **上传者当时所处的角色** | 资料由某个角色上传，即它的来源 |
| 成果 | **任务的所属角色** | 成果是某个角色的任务产出 |

**两个必须处理的边界**：

- **角色成员变更不影响已有文件**。文件已在角色目录下，改成员**不移动任何文件**。这与"MVP-004 成员是可变标签、不改写历史"一致——文件位置属于历史事实。
- **项目级资料可以没有角色**。若一份资料不属于任何角色（如客户给的原始需求文档），归入保留目录 `_shared/`。**不要**随便塞进某个角色目录，那会伪造归属。

**目录名用稳定的英文标识**，不用中文显示名（避免跨平台编码问题）：`pm` / `product` / `design` / `scenemodel` / `sceneart` / `data` / `frontend` / `backend` / `ue` / `_shared`。中文显示名只存在于库里。

#### 元数据字段

| 字段 | 用途 |
| --- | --- |
| 相对路径 | **存相对 `fileRoot` 的路径**，存绝对路径会让库换机器就失效 |
| 原文件名 | 显示用 |
| 大小 | 校验 + 展示 |
| **哈希** | 完整性校验的前提，**上传时算** |
| 版本号 | 与不可变版本对应 |

#### 两条规则

- **不做读取时校验哈希**。每次读都算哈希，大文件明显变慢，而 MVP 是单人本地使用。哈希存下来是为了**将来**能加校验，现在是零成本预留。
- **删除资料或成果时不真删文件**，只标记失效。与"历史内容只读""归档不删数据"一致。

#### 三条硬性实现要求（均由实测缺陷得出）

**一、取版本号必须与写入同事务，且用 `MAX+1` 而非 `COUNT+1`。**

```
BEGIN IMMEDIATE
  SELECT COALESCE(MAX(version),0)+1 ... WHERE 项目/角色/原名相同
  INSERT ...
COMMIT
```

外加 `UNIQUE (project_id, role, original_name, version)` 兜底。

**为什么**：`COUNT(*)+1` 在交错执行下会让两个文件都拿到 version 1，生成**相同的文件名**，一个**覆盖**另一个——直接破坏"版本不可变"。已实测复现并验证修复。

**二、写入前必须校验目标路径仍在 `fileRoot` 之内。**

```ts
const target = resolve(fileRoot, ...parts)
const rel = relative(fileRoot, target)
if (rel.startsWith('..') || isAbsolute(rel)) throw new WorkbenchError('PATH_ESCAPES_FILE_ROOT')
```

**为什么**：`path.join` 不防穿越，`path.relative` 遇到越界**也不报错**（静默返回 `..\..\` 开头的路径）。构造 `project_id = ../../../../x` 即可写出 `fileRoot`——已**真实写出文件**验证。

**必须对 `project_id` 与 `role` 同时生效**，只校验 `source_path` 不够：穿越来自**输出路径的组成部分**。

> 注意区分：`source_path` 可指向任意位置是**有意设计**（无权限，ADR-0003）；但**输出路径必须受约束**。"读哪里"是已接受的取舍，"写哪里"不是。

**三、返回对象中不得出现值为 `undefined` 的键。**

```ts
// 坏：整个返回值会被宿主拒绝
return { ok: true, warning: cond ? 'X' : undefined }
// 好
return { ok: true, ...(cond ? { warning: 'X' } : {}) }
```

**为什么**：`JSON.stringify` 会丢掉 `undefined` 键，导致"无损 JSON"校验失败，宿主拒绝整个返回值。**工具执行成功但模型拿不到结果**——静默失败。实测报错 `value is not lossless JSON`。

#### 建议（非 MVP 硬性要求）：大文件改用流式

**MVP 不做此优化**，先用"整文件读入内存"的朴素写法即可——实现更简单，且实测 200 MB 耗时 227 ms，对本地单人使用完全够用。

**但要知道代价**：`readFileSync` 会把整个文件读进内存，**内存占用等于文件大小**。上传一个 2 GB 的三维资产就会占约 2 GB 内存，可能直接失败。

**将来若需要，改法**：用 `createReadStream` / `createWriteStream` **边读边写、边算哈希**，内存占用变为常量（约几十 KB，与文件大小无关）。

**什么时候该改**：当实际要处理的单个文件接近或超过可用内存的几分之一时。在那之前，这条只是备用方案，不建议提前优化——流式写法还要额外处理背压（backpressure）与读写失败时的半成品文件清理，复杂度明显高于朴素写法。

#### 上传怎么发生

ACP 的能力清单明确返回 `promptCapabilities: { image: false, audio: false, embeddedContext: false }`，**不能通过 ACP 提示词直接传文件内容**。

MVP 采用：**工具接收绝对路径**，由插件完成"读入 → 算哈希 → 落盘到 `fileRoot` → 登记元数据"。

**代价**：上传者与插件必须能访问**同一文件系统**。对本地单人使用无碍，但这把"无权限"的边界暴露得更明显——任何调用方都能指定任意路径读取。

✅ **这条链路已实测通过**：文件落盘位置、逐字节一致性（文本 / 二进制 / 200 MB 大文件）、哈希、相对路径、同名追加新版本、失败不留残留——全部验证。细节见[实现前验证清单](项目管理工作台需求文档MVP/docs/验证/实现前验证清单.md)第七节。

⚠️ **但实测同时暴露了两个真实缺陷**，已在上方"三条硬性实现要求"中给出修复：并发版本撞号、路径穿越可写出 `fileRoot`。**实现时必须采用修复版写法**，不要照抄朴素版本。

## 三、实现顺序与验收

### 3.1 建议的推进方式

**每个模块都做成"可独立验证的纵切"**：domain 类型 → 仓储 → service 规则 → 工具 → 用 ACP 会话试一次。

不要先把所有表建完再写业务——那样发现数据模型错了，改动成本会累积。

### 3.2 两层测试，各管一段

**为什么是两层**：ACP 冒烟能证明"整条链路通"，但慢（每次一整个模型回合），且失败时说不清是业务错还是交互错。service 单测快（毫秒级）且指哪打哪，但证明不了链路通。**两者都要，各守一段**。

| 层 | 命令 | 覆盖 | 特点 |
| --- | --- | --- | --- |
| 单元 | `pnpm test` | `domain` / `sqlite` / `service` | 内存库、毫秒级、断言精确 |
| 冒烟 | `pnpm smoke` | 插件装配 → 工具 → ACP | 真实会话、慢、证明链路通 |

`pnpm check` = 类型检查 + 单测 + 构建，**每次改动都该跑**。

**单测用内存库**（`new DatabaseSync(':memory:')`）。每个用例一套独立库，因此**不共享状态、可任意顺序跑**。这与"SQLite 是唯一权威"并不冲突——测的是同一套 schema 与迁移。

**时钟必须可注入**。`ProjectService` 接收一个 `Clock`，测试用假时钟推进时间。否则"归档幂等""成员变更不产生历史"这类断言就要依赖真实时间，变得不稳定。

**用变异测试确认测试有效**。断言写得再多，也可能全是空转。验证方法是**故意把代码改坏，看测试是否变红**：

- 把"省略 background 就存 `null`"改成存一个占位字符串 → **3 个用例变红** ✅
- 把 `PRAGMA foreign_keys` 从 `ON` 改成 `OFF` → **1 个用例变红** ✅

两次都变红，说明这些断言真的在守着行为。**新写测试时建议照做一次**，尤其是"防回归"性质的用例。

> ⚠️ 一个反直觉的事实：`node:sqlite` 的 `foreign_keys` **默认就是 `1`**（与 SQLite 命令行工具默认 `0` 不同）。所以级联删除的用例**即使不写 PRAGMA 也会通过**。仍然显式写 `ON`，是为了不依赖这个默认值。

### 3.3 第一条 CI 冒烟

把验证清单第六节的最小写法固化为冒烟测试：插件装进独立 profile，通过 ACP 调用一个 `ping` 工具。

它守住的是一条**与业务无关但会让一切失效**的底线：插件能被 ACP 调用。成本约 5 分钟，收益是避免在上面白写几千行。

### 3.4 端到端演练（MVP-032）

在空库上跑通：建项目 → 上传资料 → 分析并登记方案 → 各角色确认 → 生效生成任务 → 提交成果 → 确认完成 → 下游接收 → 全程可追溯。

**建议分两段**：先验纯状态机步骤，再验依赖 Agent 的步骤。这样失败时能立刻定位是"业务逻辑错"还是"模型交互错"。

## 四、评审时最该问的四个问题

1. **半生效有没有可能？** 任何跨多表的写入，是不是都在单事务里？
2. **历史会不会被改写？** 改成员、改资料、整改任务后，旧记录是否仍能还原当时的样子？
3. **模型会不会误调"决定"类工具？** 工具名与描述是否让"这一步是不是正式决定"一目了然？
4. **库和文件会不会脱节？** 文件不动、库改了（或反过来）时，系统会怎样？路径是否可跨机器？

这四个问题对应 MVP 最贵的四类返工。

# 项目管理工作台 MVP 需求（DSH 插件版）

本目录是[完整需求文档](../项目管理工作台需求文档/README.md)（115 条需求）的**最小实现裁剪版**。

目标不是"做小一点的完整系统"，而是回答一个问题：

> 把"资料 → Agent 分析 → 多角色确认 → 正式计划 → 任务执行 → 成果接收"这条主链路做成一个**没有界面、靠聊天驱动**的最小系统，它能不能跑通？

## 一句话定义

**一个 DeepSeek Harness 插件 `@项目助手`**，把项目资料、分析建议、方案确认、任务和成果版本存进一个 SQLite 库，通过 **ACP 协议**（`dsh --profile acp`）接受外部客户端调用，**在会话里说人话即可 —— 模型自动调用相关工具，不需要任何关键词**；**不提供界面，不做权限校验**。

## 为什么可以没有界面

DSH 已经提供会话、Agent 循环、工具调用和持久化。工作台不必再建一套交互层，只需：

1. 提供**业务工具**（上传资料、登记方案、确认、提交成果……）
2. 提供**业务状态**（SQLite 里的项目、任务、版本、决定）
3. 让 Agent 通过同一个会话驱动这些工具

人不再"点击按钮"，而是**说话**；Agent 调用工具；调用方（客户端或其他 Agent）按角色提交确认。

### 入口形态（已核实）

三者都是当前 DSH 真实存在的 profile：

| 入口 | 命令 | MVP 中的角色 |
| --- | --- | --- |
| **ACP stdio** | `dsh --profile acp` | **主入口**：向外部客户端提供 Agent Client Protocol stdio 服务 |
| headless | `dsh --profile headless --json "..."` | 脚本化 / CI 验证入口 |
| 会话内使用 | 「帮我建个项目……」 | 人在任意 DSH 会话里说人话；**不需要任何触发词或咒语** |

`headless` profile 已确认挂载 `tools`、`agent`、`session`、`jobs`、`plugin-manager`，因此插件工具在无头环境下同样可用。

## MVP 保留的 5 项核心能力

这 5 项构成主链路，缺任何一项 MVP 都不成立：

| # | 能力 | 为什么不能砍 |
| --- | --- | --- |
| 1 | **Agent 分析与建议** | 系统的差异化能力；没有它，这只是一个任务清单 |
| 2 | **方案确认门禁**（每个相关角色各确认一次后整体生效） | 全系统中枢：区分"建议"和"正式计划" |
| 3 | **任务执行与成果交接**（提交 → 确认完成 → 下游接收） | 把计划变成实际推进 |
| 4 | **固定版本与追溯**（版本不可变，决定绑定当时版本） | "统一版本管理"的立身之本 |
| 5 | **通知与待办**（区分待办 / 通知，记录已读） | 让人知道下一步该做什么 |

## 明确不做

| 不做 | 原因 |
| --- | --- |
| 任何界面（Web / 桌面 / 侧栏 / overlay） | MVP 定位：验证主链路，不验证交互 |
| 权限体系与认证（角色任免、接任、停用、登录、账号） | 已确认"完全不考虑权限"；九角色只是**标签**。但代表角色做决定时仍校验**成员资格**，见[裁剪对照表](裁剪对照表.md)变更记录 |
| 仓库整理审批（分类 / 改名 / 逻辑目录） | 高成本、低验证价值，属"整理体验"而非主链路 |
| 风险跨层传播、需求变化影响分析 | 状态机最复杂；MVP 保留"问题"但砍掉自动传播 |
| 备份恢复、运行监控、配额与预算管理 | 运维能力，与主链路无关 |
| 数据加密、凭据管理、越权防护 | 随权限一并砍掉 |
| Git 作为业务权威 | 改用 SQLite 单一权威（见 ADR-002） |

## 与完整版的关键差异

| 维度 | 完整版 | MVP |
| --- | --- | --- |
| 需求条数 | 115 | **32**（见 [MVP需求.md](MVP需求.md)） |
| 入口 | Web GUI + 人工操作 | ACP / headless / 会话触发 |
| 权威存储 | Git + LFS + SQLite（多套） | **SQLite 单一权威** |
| 角色 | 有任免、交接、停权的**权限**体系 | 仅**标签**，无权限体系；但校验**成员资格** |
| 审核 | 负责人代表角色，校验任职与分派 | **该角色的成员**以角色名提交确认（校验成员资格，不校验凭据） |
| 规模 | 70+ 后端模块 + React 前端 | **单插件**，全部工具在一个包内 |

## MVP 不做但不等于不重要

以下能力在完整版中是**必要的**，只是 MVP 阶段**刻意延后**，且 MVP 的实现必须**不妨碍**它们后续加入：

- 版本冲突的并发处理（MVP 用乐观版本号，冲突即拒绝并提示重读）
- 分析预算与用量上限（MVP 记录用量但不强制上限）
- 归档与恢复的完整核对（MVP 只做"归档后只读"）
- 成果质量判断（MVP 只校验**完整性**，不做专业质量判断）

## 术语

为避免与完整版混淆，本文沿用其术语，但语义收窄：

| 术语 | MVP 含义 |
| --- | --- |
| **项目** | 一个 SQLite 库内的顶层容器，含概览、资料、方案、任务 |
| **角色标签** | 九类字符串之一（项目管理/产品/设计/场景模型/场景美术/数据/前端/后端/UE端），**无权限含义** |
| **资料** | 上传入库的文件，有不可变版本号 |
| **方案** | 待确认的任务定义集合；全部相关角色确认后成为**正式计划** |
| **确认** | 调用方以某角色名提交的同意/拒绝记录 |
| **任务** | 有输入要求、成果要求、完成标准的工作项 |
| **成果** | 任务提交时形成的不可变产出 |
| **接收** | 下游任务确认某成果版本可供其使用 |
| **待办** | 需要反馈的事项；**通知**仅告知 |
| **`@项目助手`** | 插件包名。**不是**会话里的暗号 |
| **会话内称呼** | 人在会话里可以随口叫它「项目助手」，但**叫不叫、叫什么都与工具能否调用无关** |

## 验收方式

MVP 的验收是一次**端到端演练**（见 [MVP需求.md](MVP需求.md) 的 MVP-032）：

在空库上，通过 ACP 或会话触发，完成——

> 建项目 → 上传需求资料 → 让 Agent 分析并提出方案 → 3 个角色各确认一次 → 方案生效生成任务 → 主执行人提交成果 → 负责人确认完成 → 下游任务接收该成果 → 全程可在追溯里查到当时用的哪一版

**其中任何一步断掉，MVP 即不算完成。**

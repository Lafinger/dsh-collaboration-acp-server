# 角色是标签，不是权限

状态：**已被 [ADR-0004](0004-one-member-per-role-flat.md) 取代**（2026-10-11）

> **取代说明**：本 ADR 把角色压缩为纯标签，导致 `NOTICE-002`（成员应能找到自己承担的任务）无法实现、"待办给谁"无法回答。ADR-0004 改为「一角色一成员、全角色平级」，并**继承**本 ADR 的技术立场：不校验身份、确认以角色为键。本文件**保留以记录当时的推理**，不作为现行依据。其中"不校验身份"一条**已于 2026-10-11 修订**——见 [ADR-0004](0004-one-member-per-role-flat.md) 的修订说明与[裁剪对照表](../../裁剪对照表.md)的变更记录。

MVP **不实现任何权限、身份或任职校验**。九类专业角色（项目管理、产品、设计、场景模型、场景美术、数据、前端、后端、UE端）保留为**纯分类标签**，记录"这是谁的职责范围""这条确认是哪个角色给的"。"每个相关角色各确认一次，方案才生效"这条**门禁机制保留**，但它校验的是**确认记录的完备性**，不是提交者是否有权提交——同一调用方可以依次以产品、设计、前端的名义提交确认，系统分别记录三条。

## 为什么这是真实权衡而非偷懒

最初的完整需求（115 条）中**约 28 条**围绕权限与组织设计：任命与接任、任职校验、代表权、停用不删责任、管理员资格交接、生效时核对身份等。用户明确要求"完全不考虑权限和安全问题"，因此这些被整体裁剪。

代价是**原文档多处条款的字面语义不再成立**：原文"由每个相关角色的**负责人**代表该角色审核"包含"负责人"这一经任命、有任期的身份；MVP 中不存在负责人，只有角色名。这是本次裁剪中**最大的一处语义改写**，已在[裁剪对照表](../../裁剪对照表.md)中逐条标注（尤其 PLAN-005、PRJ-006~014）。

## 考虑过的方案

- **简化为"单一人类确认一次"**：更小。**未采用**：会让 MVP 失去它最想验证的东西——建议经多角色分别确认后才成为正式计划，这是整个系统的中枢。
- **由 Agent 代为逐角色确认**：流程最顺。**未采用**：确认门禁会退化为 Agent 自问自答，失去验证价值。
- **保留权限但只做最简实现**：会重新引入用户已明确排除的复杂度。

## 后果

- MVP **不能用于多人真实协作**：任何调用方都能以任何角色名义提交确认。这是**有意的**，不是缺陷。
- 九角色标签因此成为**弱约束**：它们影响"要收齐哪几条确认"，不影响"谁可以提交"。
- 后续若恢复权限，须在**确认记录**上增加提交者身份校验，而不是重建数据结构——本 ADR 的数据形状是为此预留的。

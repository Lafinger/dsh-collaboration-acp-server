# SQLite 作为 MVP 的唯一状态权威

状态：已采用

MVP 的全部业务状态——项目、资料版本、分析记录、方案、角色确认、任务、成果、接收决定、待办——都存进**一个 SQLite 库**，插件进程直接读写；文件字节存在同级附件目录里，库里只存相对路径与元数据。没有第二套权威，不做 Git 业务仓、不双写。

## 考虑过的方案

- **Git 作为业务权威**：与工作区 `Experiment/` 的既有决定（`docs/decisions/0001`、`0003`）一致，天然带版本与历史。**未采用**：需要处理 commit、分支、锁与合并冲突，而 MVP 要验证的是主链路能否跑通，不是版本控制的工程质量；且无界面意味着冲突无法交给人工在界面上解决。
- **SQLite 存状态 + Git 存文件历史**：能力最全。**未采用**：两套权威需要一致性协议，是 MVP 阶段最大的复杂度来源。
- **纯文件系统（JSON/YAML）**：无依赖。**未采用**：方案确认、成果接收这类"多对象一次性原子生效"的操作难以保证不出现半完成状态。

## 后果

- **不可逆程度高**：后续若改为 Git 权威，等于重写持久层，因此现在记下。
- **与 `Experiment/` 的 ADR 0001/0003 直接冲突**：那两个 ADR 仍描述其自身系统，不适用于 MVP；两份文档并存时以本文为准，不要互相引用。
- MVP 因此**放弃**"库可丢、可由 Git 重建"的假设。SQLite 库就是唯一真相，**备份与恢复是 MVP 明确不做的能力**（见[裁剪对照表](../../裁剪对照表.md) OPS-009/010 删除条目）——这是一个已知且有意接受的缺口。
- 并发写入靠 SQLite 自身事务；跨对象的"整体生效"（方案生效、完成交接）必须在**单个事务**内完成，否则会出现半完成状态。

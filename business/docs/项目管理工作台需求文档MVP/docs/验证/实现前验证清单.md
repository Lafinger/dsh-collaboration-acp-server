# 实现前验证清单：DSH 插件在 ACP 下的可达性

本文记录**已实际执行**的最小验证，供实现 MVP 时复用。核实日期 2026-10-11。

**验证目标**：证明"自定义插件的自有工具，能被 ACP 会话调用"。这是 MVP 全部业务能力的前提——在写任何业务逻辑之前必须先确认。

**验证结果：通过。** 实测输出：

```
initialize   -> OK
session/new  -> a3f4ca4c-3920-4690-ac7b-91d9a926fcd0
[tool_call] ping_probe
[text] ... The exact token it returned is: **`PING-PROBE-OK`** ...
session/prompt -> {"stopReason":"end_turn"}

RESULT : custom tool called = true ; token returned = true
```

这比"配置里挂着 `tools` 插件"强得多：那是静态推断，这是**模型真实调用自定义工具并拿到返回值**。

---

## 一、最小验证用了什么

一个三文件的插件，**纯 ESM JavaScript，无构建步骤**（刻意如此，以隔离"打包"这个变量）：

```
acp-ping-probe/
├── package.json          # name / type:module / main / dsh.bundle.patch / peerDeps(*)
├── cordis.patch.yml      # 声明插件挂载点
└── index.js              # 一个 ping_probe 工具
```

关键实现（`index.js`）：

```js
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'acp-ping-probe'

export function apply(ctx, config) {
  ctx.inject(['tools'], (toolCtx) => {
    toolCtx.tools.register(defineTool({
      name: 'ping_probe',
      description: '...',
      parameters: { note: { type: 'string' } },
      output: {
        schema: { type: 'json' },
        render: (_args, value) => [{ type: 'text', text: JSON.stringify(value) }],
      },
      execute(args) { return Promise.resolve({ ok: true, token: 'PING-PROBE-OK', ... }) },
      presentCall: (args) => ({ card: 'generic', title: 'Ping probe', kind: 'other', rawInput: args }),
    }))
  })
}
```

**与 `DSH-taskboard` 的写法一致**（见其 `src/tool/index.ts` 的 `registerTaskboardTools`：`ctx.tools.register(definition)`）。`defineTool` 确实存在于 `@deepseek-ai/dsh-tools@0.1.5-rc.2`（已实测确认）。

## 二、执行步骤（可照抄）

设 `DSH` 为 dsh 命令，`PROBE` 为插件目录绝对路径。

### 1. 建一个**独立 profile**，不要动现有 profile

```sh
dsh --profile probetest --from-default-profile acp --dump-config
```

从内置 `acp` 模板派生一个名为 `probetest` 的 profile。

> **为什么必须独立**：验证会改写 profile 的 `package.json`、lockfile 和 `node_modules`。用独立 profile 才能在出问题时直接删掉，且不污染你正在使用的 `acp` / `web` profile。本次验证后已确认：真实 `acp` profile 的 `package.json` 中 `dependencies` 仍为 `{}`，未被触碰。

### 2. 安装插件

```sh
dsh plugin --profile probetest add -w "$PROBE"
```

> **`-w` 必须带**。profile 目录本身是 pnpm workspace 根；不加 `-w` 会报 `ERR_PNPM_ADDING_TO_ROOT`。
>
> 本次输出：`+ acp-ping-probe link:...`，耗时 312ms。

### 3. 检查三个安装标记（缺一不可）

```sh
cat ~/.dsh/profiles/probetest/package.json
ls -l ~/.dsh/profiles/probetest/node_modules/
```

| 检查 | 期望 | 本次实测 |
| --- | --- | --- |
| `dependencies` 含插件名 | 出现 `link:<绝对路径>` | ✅ |
| `dsh.profile.bundles` 列出插件，且在 `@deepseek-ai/dsh-base` **之后** | `dsh-base > dsh-acp-app > acp-ping-probe` | ✅ |
| `node_modules/<插件名>` 存在 | 符号链接指向源目录 | ✅ |

### 4. 验证组成层（不启动服务）

```sh
dsh --profile probetest --dump-config | grep -A2 'acp-ping-probe'
```

期望出现：

```yaml
# == acp-ping-probe
- id: acp-ping-probe
  name: acp-ping-probe
```

本条**必过**。若这里就没有，后面不可能成功——问题在 `dsh.bundle.patch` 或 `bundles` 顺序，不在业务代码。

### 5. 用 ACP 会话调用工具

用一个最小 ACP 客户端（见下方"驱动要点"），`session/prompt` 内容：

> Call the `ping_probe` tool with note "mvp-verify". Then report the exact token it returned.

**通过标准（两条都要）**：

1. 收到 `session/update` 中 `sessionUpdate: "tool_call"`，且工具名为 `ping_probe`
2. 模型回复中出现工具返回的 `token` 原文

只看第 1 条不够——那只能说明工具被"展示"，不能说明**执行成功并回传了结果**。

## 三、驱动 ACP 的三个坑（都实际踩过）

### 坑 1：不要经 `cmd.exe` 或 `shell: true` 启动

`dsh` 是 `.cmd` 垫片，且安装路径含空格。用 `shell: true` 或 `cmd.exe /c "..."` 都会把路径切错，实测报：

```
'C:\Users\cjh13\AppData\Local\Programs\DeepSeek' is not recognized as an internal or external command
```

或 `The network path was not found.`

**正确做法**：直接 spawn `DeepSeek Harness.exe`，传参数组，并设 `ELECTRON_RUN_AS_NODE=1`：

```js
spawn('C:\\...\\DeepSeek Harness.exe',
  ['--expose-internals',
   'C:\\...\\resources\\app.asar\\dsh\\node_modules\\@deepseek-ai\\dsh-desktop-host\\lib\\cli.js',
   '--profile', 'probetest'],
  { stdio: ['pipe','pipe','pipe'], env: { ...process.env, ELECTRON_RUN_AS_NODE: '1' } })
```

（这正是 `dsh.cmd` 内部所做的事。）

### 坑 2：Agent 发来的请求必须应答

`session/update` 是**通知**（无 `id`），忽略即可。
但 `session/request_permission` 是**请求**（有 `id`），**不应答会让回合永远挂住**。

```js
if (m.method && m.id !== undefined) {
  send({ jsonrpc:'2.0', id:m.id, result:{ outcome:{ outcome:'selected', optionId:'allow_once' } } })
}
```

本次 `ping_probe` 未触发权限请求（工具无副作用），但一旦工具会读写文件或跑命令就会触发。

### 坑 3：启动要等，别提前判定失败

ACP 进程启动有延迟。客户端需给足够超时（本次设 180s），否则会在初始化前误报超时。

## 六、TypeScript 构建补验（已通过）

针对第五节遗留的"TS 构建产物"风险，已补做验证并**通过**。过程中发现两个**必踩的坑**，都是静默失败——不报错、不提示，只是工具不出现。

### 6.1 结论先行：可用的最小写法

```ts
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-plugin'

export function apply(ctx: Context): void {
  ctx.inject(['tools'], (toolCtx) => {
    toolCtx.tools.register(defineTool({          // ← 必须用 defineTool 包装
      name: 'my_tool',
      description: '...',
      parameters: { note: { type: 'string' } },
      output: {                                   // ← 必须声明
        schema: { type: 'json' },
        render: (_a, v) => [{ type: 'text', text: JSON.stringify(v) }],
      },
      execute: (args) => Promise.resolve({ ok: true }),
      presentCall: (args) => ({ card: 'generic', title: '...', kind: 'other', rawInput: args }),
    }))
  })
}
```

实测输出：`[tool_call] ts_probe` → `{"ok":true,"token":"TS-BUILD-OK",...}`。

### 6.2 坑一：必须用 `defineTool()` 包装，裸对象会被静默丢弃

**裸对象字面量注册会失败**，且失败方式极隐蔽：

- `ctx.tools.register({...})` **不抛异常**（注册看着成功了）
- `--dump-config` **显示插件已加载**
- `apply()` **确实被调用**
- 但工具**不在模型的工具表里**，模型会说"没有这个工具"

正确做法是包一层 `defineTool({...})`。裸对象与 `defineTool` 包装在**其他方面完全等价**，只差这一层。

**Agent 侧只看到症状**：一个 `-32603` 错误

```
Invalid schema for function 'ts_probe': schema must be a JSON Schema of 'type: "object"', got 'type: null'
```

`type: null` 是**裸对象未被转换**的指纹。看到这个报错，先检查有没有漏 `defineTool`。

### 6.3 坑二：`output` 必填，且 `schema.type` 受 SDK 版本约束

`register()` 会在**运行时**校验 `output`，缺失即抛：

```
tool "ts_probe" must declare output { schema, render, presentationMeta? }
```

`output.schema.type` 的合法值随版本变化：

| 写法 | `dsh-tools@0.1.5-rc.2`（宿主实际版本） |
| --- | --- |
| `{ type: 'json' }` | ✅ 可用（**但必须包在 `defineTool` 里**） |
| `{ type: 'json' }` 裸对象 | ❌ `unsupported JSON schema: schema.type must be one of object/array/...` |
| `{ type: 'object', properties: {...} }` | ✅ 可用 |

### 6.4 版本错配是根因，且值得警惕

| 组件 | `@deepseek-ai/dsh-tools` 版本 |
| --- | --- |
| 宿主运行时实际提供 | **`0.1.5-rc.2`** |
| `DSH-taskboard` 声明依赖 | `0.1.6-alpha.1` |

**taskboard 是按 `0.1.6-alpha.1` 写的，而宿主给的是 `0.1.5-rc.2`。** SDK 的 schema 校验规则在两个版本间**不兼容**。

因此：**不能照抄 taskboard 的写法而不在本机验证**。它的代码是它那个版本的正确答案，未必是本机这个版本的正确答案。

➡️ **对策**：以本机实测为准；把 6.1 的最小写法作为模板；每次升级 DSH 后重跑第六节的验证。

### 6.5 另一个真实的坑：`tsc` 默认"有错也产出"

TypeScript 默认**即使类型报错也照样生成 `lib/`**。本次一开始 import 无法解析（`Cannot find module '@deepseek-ai/cordis'`，因为依赖尚未安装），但 `lib/index.js` **仍被生成**。

若 CI 只看"文件是否生成"，会**静默通过一个类型全错的构建**。

➡️ **对策**：构建脚本用 `tsc --noEmitOnError`，或 `typecheck`（`--noEmit`）与 `build` 分开且都设为必须通过。`DSH-taskboard` 正是这么做的（它有独立的 `typecheck` 脚本）。

### 6.6 顺带确认

- DSH 内置 Node 为 `24.18.1`（系统 Node 为 `24.15.0`），**两者都自带 `node:sqlite`**，`BEGIN IMMEDIATE` 实测可用 → MVP 的 SQLite 事务方案不依赖外部数据库驱动。
- 插件在 profile 下的符号链接位置是 `~/.dsh/profiles/<profile>/node_modules/<插件名>`。**注意不要错看成 `~/.dsh/profiles/node_modules/`**（那是共享根，不含 profile 自己的插件）——本次验证时我曾据此误判"链接丢失"，实际链接正常。

## 七、上传链路补验（已通过）

针对第五节遗留的"上传链路"风险，已补做验证并**通过**。这是 M2 全部功能的地基。

### 7.1 验证方法

写了一个真实实现上传链路的插件（**不用 mock**），经真实 ACP 会话驱动：

```
工具接收绝对路径 → 读入 → 算 sha256 → 落盘到 fileRoot
                → 按 <项目ID>/<角色>/materials/<资料ID>/v<版本号>__<原文件名> 组织
                → 写元数据进 SQLite
```

然后**独立**从文件系统和数据库两侧核对结果——不采信工具自己的返回值。

### 7.2 逐项结果

| # | 检查项 | 结果 |
| --- | --- | --- |
| 1 | 文件真的落到 `<项目ID>/<角色>/` 下的角色目录 | ✅ `PRJ-1/product/materials/1/v1__设计稿 v1 (最终版).txt` |
| 2 | 落盘内容与源文件**逐字节一致** | ✅ 独立重算 sha256 相符 |
| 3 | 工具上报的 sha256 与真实文件哈希一致 | ✅ 一致 |
| 4 | 元数据真的进了 SQLite | ✅ 9 个字段齐全 |
| 5 | `rel_path` 存的是**相对路径**而非绝对路径 | ✅ 以 `PRJ-1/` 开头，无盘符 |
| 6 | 同名再次上传**不覆盖**，而是追加新版本 | ✅ v1 与 v2 **同时存在**于不同目录 |
| 7 | 两个版本内容确实不同 | ✅ size 62/79，哈希不同 |
| 8 | 源文件不存在时**不半写** | ✅ 返回 `SOURCE_NOT_FOUND`，无孤儿行 |
| 9 | 失败调用未留下任何数据库残留 | ✅ 行数仍为 2，无空路径 |

**关键结论**：目录结构、哈希、相对路径、版本追加、失败回滚——**五项全部按设计工作**。

### 7.3 两个值得注意的观察

**观察一：原文件名被原样保留，含空格与全角括号。**
`v1__设计稿 v1 (最终版).txt` 里空格与括号都在。这验证了"用 ID 做目录、原文件名只当显示名"的设计是必要的——**如果当初用原文件名做目录，这个路径早就出问题了**。同时它也是个提醒：下游若有消费方假设路径是 URL 或 shell 安全的，会踩坑。

**观察二：模型的自我校验行为可靠。**
第 8 项失败场景中，模型明确说"调用失败，没有值可报告"，并原样回传结构化错误，**没有编造** `rel_path` 或 `sha256`。这说明只要工具返回诚实的错误对象，模型不会硬凑答案。

### 7.4 四项遗留风险已补验（发现两个真实缺陷）

第七节原先列出了四项未覆盖。补验后**两个通过、两个发现真实缺陷**。

| # | 检查项 | 结果 |
| --- | --- | --- |
| 1 | **二进制文件完整性** | ✅ **通过**。2 KB 二进制（含 NUL 与高位字节）逐字节一致，独立重算 sha256 相符 |
| 2 | **大文件（200 MB）** | ✅ **通过**。逐字节一致，耗时 **227 ms** |
| 3 | **并发上传版本撞号** | ❌ **缺陷确认**（见 7.5） |
| 4 | **路径穿越** | ❌ **漏洞确认**（见 7.6） |

**大文件结论的边界**：227 ms 是**热缓存、单次采样**，不能代表最坏情况的吞吐。且朴素实现用 `readFileSync` 把整个文件读进内存——**内存占用等于文件大小**（200 MB 文件约占 200 MB 内存）。

> **这不是 MVP 的硬性条件**。本地单人使用下朴素写法完全够用，建议先用简单实现。将来若要处理接近可用内存量级的三维资产或视频，再改为流式（`createReadStream` 边读边算哈希边写），届时内存占用变为常量。详见[具体核心实现](../../../../docs/具体核心实现.md)的"建议（非 MVP 硬性要求）"一节。

### 7.5 缺陷一：并发下版本号撞号

**朴素写法**（`version = COUNT(*)+1`）在交错执行下会撞号。实测：

```
reader A saw count = 0 -> will assign version 1
reader B saw count = 0 -> will assign version 1
resulting rows: [{"id":1,"version":1,"sha256":"sha-A"},{"id":2,"version":1,"sha256":"sha-B"}]
VERSION COLLISION : YES - CONFIRMED
```

**后果比"重复行"更严重**：两个不同文件都拿到 version 1，生成的文件名完全相同（`v1__x.txt`），**其中一个会覆盖另一个**——直接破坏"版本不可变"这条核心保证。

**修复**（已实测有效）：把取号与写入放进**同一个 `BEGIN IMMEDIATE` 事务**，并用 `MAX(version)+1` 而非 `COUNT(*)+1`：

```
BEGIN IMMEDIATE
  SELECT COALESCE(MAX(version),0)+1 FROM materials WHERE 项目/角色/原名相同
  INSERT ...
COMMIT
```

再加一条 `UNIQUE (project_id, role, original_name, version)` 作为兜底（实测能正确拒绝重复插入）。

修复后实测：`[{"version":1},{"version":2}]` → **COLLISION: NO**。

> MVP 是单人本地使用，撞号概率低。但**修复成本极低**（一个事务 + 一条唯一约束），而代价是静默覆盖文件，建议**直接采用修复版**。

### 7.6 缺陷二：路径穿越可写出 `fileRoot`

**这是本次最严重的发现。**

`project_id` 与 `role` 被**未净化地**拼进路径。构造 `project_id = ../../../../ESCAPED` 即可逃出 `fileRoot`。已**真实写出文件**验证（非仅推测）：

```
computed dir : C:\Users\cjh13\Desktop\项目管理工作台\ESCAPED-BY-TRAVERSAL\product\materials\99
wrote file   : ...\v1__secret.txt
EXISTS       : true
```

**两个加重情节**：

1. **`path.join` 不防穿越**——它只负责拼接，会把 `..` 原样保留。
2. **`path.relative` 不报错**——目标在 `fileRoot` 之外时，它**静默返回 `..\..\...` 开头的相对路径**，不抛异常。所以"存相对路径"这个设计本身**不会**发现越界；朴素的 `startsWith('..')` 检查还发生在 `copyFileSync` **之后**，即**写已发生**。

**修复**（已实测有效）：写入前先 resolve，再要求结果必须落在 `fileRoot` 之内，否则拒绝：

```
target = resolve(fileRoot, ...parts)
rel = relative(fileRoot, target)
if (rel.startsWith('..') || isAbsolute(rel)) throw PATH_ESCAPES_FILE_ROOT
```

实测：合法路径放行，`../../../../ESCAPED` 与 `..\..\ESCAPED` 两种形式**均被拦截**。

**必须同时对 `project_id` 和 `role` 生效**，只校验 `source_path` 不够——穿越来自**输出路径的组成部分**，不是输入文件。

> ⚠️ 注意：`source_path` 允许任意路径是**有意设计**（MVP 不考虑权限，见 ADR-0003）。但**输出路径必须被约束**——这两件事不同：前者是"读哪里"，后者是"写哪里"。读任意文件是已接受的取舍，**写到任意位置不是**。

### 7.7 意外发现：返回对象含 `undefined` 会导致工具输出被丢弃

探针最初返回 `warning: escapes ? '...' : undefined`，结果**整个工具返回值被宿主拒绝**：

```
Error: tool "material_upload" returned invalid output: value is not lossless JSON
```

**原因已机械验证**：`JSON.stringify` 会**丢掉**值为 `undefined` 的键，因此序列化后再解析**键数不一致**（3 → 2），不满足"无损 JSON"。

**这是静默失败**：工具**执行成功**（文件和数据库都已写入），但**模型拿不到返回值**。模型只能靠翻数据库和日志反推结果——它做对了，但这**不该是常态**。

**规避**：返回对象中**不要出现值为 `undefined` 的键**。要么省略该键，要么用 `null`。

```js
// 坏：键存在但值为 undefined，整个返回被拒绝
return { ok: true, warning: cond ? 'X' : undefined }

// 好：条件性地展开
return { ok: true, ...(cond ? { warning: 'X' } : {}) }
```

移除此键后，工具输出恢复正常送达。

### 一个真实事故：变异脚本被中断留下了变更

一次变异运行超时被终止，**把"完成即自动接收"这个变异留在了源码里**，导致 **16 个无关测试失败**，看起来像是修复引入了回归。

## 十一、第二轮：证据本身可靠吗（已通过）

第二轮不再问"功能对不对"，而是问一个更难的问题：**我手上这些证据，本身可靠吗？** 结论是：**两个结构性问题**。

### 问题一：36 个源文件零变异覆盖

审计给 **14 条需求**评的是 ADEQUATE —— **有测试，但没有证据表明测试会失败**。没人见它红过的测试只是猜测。

新建 scripts/mutate-adequate.cjs 专门打这批需求，**10 项全被抓、0 存活**，其中一项抓出真缺口：

> **MVP-018 缺口**：`rolesReason` 在约 50 处被传入，**但没有任何地方断言过它的值**。把它截断成空字符串，**263 个测试全绿通过**。

已补测试（断言值本身、且修订后记的是新理由），变异随即被抓。

### 问题二：五个变异脚本都没有中断保护

上一轮那次"残留变异导致 16 个无关测试失败"的事故，**成因一直还在**：脚本就地改写源码，被杀就留下变更，**此后"基线"不再是真实代码，每个判定都在描述错误的对象**。

抽成 scripts/mutation-harness.cjs，六个脚本统一三道防护：

| 防护 | 作用 | 已实测 |
| --- | --- | --- |
| **预检** | 拒绝在已变异的代码上运行 | **是** —— 输出 `REFUSING TO RUN`，退出码 1 |
| **恢复** | 每轮 + 信号 + 异常路径都还原 | 是 |
| **校验** | 结束时比对快照，不一致即失败 | 是，六套均输出 `source verified clean` |

### 本轮的诚实结论

**"修好了"与"证明修好了"是两件事，"有测试"与"测试会失败"也是两件。** 这一轮修的全是第二类问题 —— 功能没坏，**是证据不硬**。

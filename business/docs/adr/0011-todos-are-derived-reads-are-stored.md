# 待办是推导出来的，只有"已读"落表

状态：已采用

M6 要回答"谁该做什么"。三个来源——**方案确认**、**成果确认**、**成果接收**——都已经在库里是权威记录，所以待办**不另存一张表**，而是从这些槽位推导。

## 待办是槽位的投影

| 待办类型 | 来源表 | 槽位身份 |
| --- | --- | --- |
| 方案确认 | `confirmations` | `(plan_id, plan_version, role)` |
| 成果确认 | `result_confirmations` | `(result_id, version)`，角色随任务 |
| 成果接收 | `acceptances` | `(result_id, version, task_id)` |

**三个来源都已经有稳定、唯一的槽位身份**（前两者各有 UNIQUE / PK 约束保证），所以**不需要引入代理 ID**：待办的身份就是 `(类型, 对象, 角色)`。

## 为什么不建待办表

如果另存一张 `todos` 表，**立刻产生同步问题**：任务被取消了，那张待办谁删？方案被修订、确认槽位作废了，待办跟着废吗？

**这些问题在 MVP 里没有便宜的解法**，而推导**不可能不一致**——待办是否该存在，就是槽位当前状态的函数。

**代价要说清**：每次查询要聚合几张表。MVP 规模下不构成问题；任务上万时需要再评估。

## 只有"已读"必须落表

**已读推导不出来。** 库里没有任何其他地方记录"谁看过这条待办"，所以它是**推导方案的必要例外**，必须落表。

### 已读按角色槽位记录，不按人

MVP-030 明文"已读**按角色槽位记录**"。所以：

```
reads 的主键 = (待办身份, 角色)
```

**不是** `(待办身份, 成员)`。

这与 MVP 的全局设计一致：**确认属于角色，不属于人**。一个角色换人之后，之前以该角色身份读过的，仍是该角色读过的。

### 角色空缺时不产生未读

MVP-030 与关键规则都要求：**槽位存在但无成员时，待办仍可查询并显示"角色空缺"，但不产生未读**。

这是**推导出来的**，不是存下来的：当角色没有成员，其余数为 0，**不需要一条"没有未读"的记录**。

> 这一条如果不做，会让"未读"显示成一个**空的角色欠了多少事**，而那个角色根本没人能来处理它。

## 未读 = 该角色的未决槽位 − 该角色已读的

```
未读(角色) = |{ 待办类型属于该角色，且槽位未决 }| − |{ 这些待办中该角色已读的 }|
```

**未读数量不为负**是这条定义的自然结果，不需要额外夹紧——已读只能针对已存在的待办，而待办一旦决出就不再计入。**有测试专门验证不为负和重复读取不重复计数**（靠主键约束，不是靠计数逻辑）。

## 通知与待办同表不同类

两者的区别是**需不需要反馈**，字段几乎相同。分成两张表会让"某人所有未处理事项"变成一个 union。

**但两者的行为必须不同**：

- 读**待办不产生任何业务决定**（MVP-030），已交付的待办**不因读取而消失**——完成待办只能通过**提交对应决定**。
- 读**通知**同样不产生决定。

## 排除的方案

**建 `todos` 表。** 否掉：立刻带来"槽位作废时待办怎么办"的同步问题，而推导不会不一致。

**已读按人记录。** 否掉：与 MVP-030"按角色槽位记录"直接矛盾。

**给槽位空缺的角色也记未读。** 否掉：违背"角色空缺的待办不产生未读"，且会让未读显示成无人能处理的欠账。

**通知单独建表。** 否掉：字段几乎相同，查询会变成 union。

## 空缺角色不能作出任何决定

**这不是原本的设计，是 M6 冒烟测试逼出来的。**

冒烟时模型报了一个它自己发现的"反常"：`design` 角色**在 `project_roles` 里连一行都没有**，却**照样确认了方案、也做了成果接收**——只靠 `submitted_by` 记了个名字。

查证属实。MVP-019 说"角色空缺时方案**停在等待并提示**"，但**没写"禁止该角色确认"**，所以代码的行为不违背字面要求。**可是一旦任何人都能替空缺角色确认，"空缺"就退化成纯展示**——传个名字就能通过。

**已按"拒绝"处理**：`plan_confirm`、`result_review`、`result_accept` 三处都校验该角色是否有成员，没有则 `VACANT_ROLE_CANNOT_CONFIRM`。

**为什么这是对的**：空缺**不是**一个待补的手续，它意味着**项目还没说这件事归谁**。既然没人担任，**就不存在"他的同意"可以记录**。

> **边界**：这条**加强了** MVP-019，没有改变它——"停在等待"从此是**硬约束**，而不是提示。加载冒烟里它确实挡住了：`design` 的 `outcome` 始终为 `null`，任务数与生效方案数都是 **0**。

## 后果

- **只有 `reads` 一张新表**，主键 `(kind, object_ref, role)`。
- **待办没有"创建"动作**，因此 MVP-016"禁止自动创建任务"在这里不可能被违反——这一层根本不写业务对象。
- **待办查询是只读的**：`todo_list` 不改变任何业务状态。
- 本层**不实现推送**：没有投递、没有订阅、没有后台。ACP 会话按需查询。
- "已读"**不能**用于表示同意、完成、接收或解决——有测试断言标记已读后业务状态不变。

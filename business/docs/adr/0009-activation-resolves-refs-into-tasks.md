# 生效是一次解析：任务在方案生效的那一刻才诞生

状态：已采用

方案生效时，把方案里的**提案**变成**真实任务**。这个过程按固定顺序执行，且**两处校验**。

## 生效的六个步骤

```
1. 校验：add 的 ref 唯一；modify/cancel 的目标任务存在、未完成、未取消
2. 建所有 add            → 得到 ref → task_id 映射
3. 用映射解析每个任务的依赖 → 连同内容写入该任务版本
4. 处理 modify           → 各自产生新版本
5. 处理 cancel           → 标记终止
6. 写账本 plan_task_outcomes
```

**全部在单个事务内。** 任一步失败则整体回滚，方案停在待生效状态。

## 为什么必须两遍

一个方案版本里可以同时有 `{ref:"t1", change:"add"}` 和 `{ref:"t2", change:"add", depends_on:["t1"]}` —— **依赖指向本次才新建的任务**。

一遍处理时 `t1` 的 `task_id` 可能尚未生成。所以顺序是**先建全部 `add`，再解析依赖**。这不是优化，是语义要求。

## 为什么要两处校验

**登记时**校验，是为了让错误在**尚未收确认**时暴露（代价最小，与 MVP-017 拒绝成环同一理由）。

**生效时**再校验，是因为**状态会在收确认的窗口里改变**：登记时某任务未完成，收确认期间它可能被完成了。若只在登记时校验，"修改已完成任务"就会通过，**ADR-0008 的冻结保证被破坏**。

**代价要说清**：方案可能在**收齐确认后仍然失败**。这看似很糟，但比悄悄改掉一个已完成的任务好得多。失败是原子的，方案停在待生效，人可以 `plan_revise` 重来。**生效失败的说明必须点名是哪个任务、什么原因**，否则无法修。

## 排除的方案

**只在登记时校验。** 否掉：中间窗口内状态会变，冻结保证失效。

**只在生效时校验。** 否掉：错误暴露太晚，且登记阶段本可以廉价发现。

**依赖与 `add` 一遍处理。** 否掉：依赖会指向尚未生成 ID 的任务。

## 后果

- `modify` 的合法目标 = **未完成且未取消**的任务。
- `cancel` / `modify` 同一个任务出现两次 → 拒绝（`DUPLICATE_TASK_TARGET`）。同份方案里改两次语义含糊，MVP 没有"合并两次修改"的概念。
- **生效失败是一个正常结果**，不是异常。工具必须把失败原因表达成可操作的信息。
- 正式计划**不再单独存一份任务清单**：`plan_task_outcomes` 账本已经回答了"这份方案生效时每个 ref 变成了什么"。存第二份就会不一致。

# 归档是只读的，且写入口必须只有一个判据

## 背景

MVP-005 的原文很短：

> 项目可归档；归档后业务只读，不再接受新的**资料、方案、任务或成果**写入。

**一句话，覆盖四类写入。** 而实现里"是否可写"这个判断**散落在各个 service 自己身上**，谁想起来谁写。

## 问题：五个写入口，只有两个有判断

M7 完成后的一次审计把每个写入口都跑了一遍（归档后逐个调用），结果：

| 写入口 | 归档后 |
| --- | --- |
| 上传资料 | **被拒** |
| 登记方案 | **被拒** |
| 改角色成员 | **被拒** |
| 记进展 | **写入成功** |
| 提交成果 | **写入成功** |
| 提交分析 | **写入成功** |

**归档后的项目还能继续收分析、收进展、收成果。** 库里确实多了行，不是"看起来像"。

> **探测时踩过一个坑**：第一次探测 `analysis_submit` 报的是 `SCOPE_REQUIRED`，**看起来像"已经拦住了"**。实际是**我传了空 scope**，它在更早的地方就被拒了。换成**合法 scope** 才暴露出归档完全没被检查。**一个错误的探测方法会给出"一切正常"的假象。**

## 为什么写成"各 service 自己判断"必然漏

因为**判据是同一个，但代码是五份**。漏的那三处不是有人写错了，而是**没人想起来要写**：

- `material-service` 有 `requireWritableProject`
- `plan-service` 有 `requireWritableProject`
- `analysis-service`、`result-service` **完全不引用 `archived`**
- `task-service` 同理

**同一个规则有五个副本，就等于有五个可能不一致的地方。** 这不是态度问题，是结构问题。

## 决定一：判据收进 domain，全项目一份

新增 `assertWritable(project, projectId)`，放在 `domain/project.ts` —— **规则属于项目，不属于恰好正在写的那个 service**。

五个 service 一律调它，**不再各写一份**：

- `project-service.requireWritable` → 转发
- `material-service.requireWritableProject` → 转发
- `analysis-service.submit` → 调
- `result-service`（进展、提交、审查、接收、开槽位）→ 调

**收拢之后，"哪条路径忘了判断"这个问题从"要读完五个文件"变成"搜一个函数名"。**

## 决定二：漏掉的三条路径补上判断

补的位置是**每一个产生新记录的动作**，不只是最显眼的两个：

| 路径 | 为什么算写入 |
| --- | --- |
| `analysis.submit` | 产生一条分析 |
| `result.addProgress` | 产生一条进展 |
| `result.submit` | 产生一个成果版本 |
| `result.review` | 产生一条决定 |
| `result.decide` | 产生一条接收决定 |
| `result.openAcceptances` | 产生确认槽位 |

**"读"不受影响**：`get`、`listByProject`、`material.read` 在归档后**照常可用**。需求说的是**只读**，不是**消失**。

## 决定三：拒绝时的错误码统一为 `PROJECT_ARCHIVED`

不做成"每个 service 用自己的说法"。调用方需要能**稳定地**分辨"因为归档所以不行"，**一个码就是一份可判定的合同**。

## 同类问题：拒收通知发错了人（MVP-027）

**同一个"判据写错地方"的病，换了个样子。**

MVP-027 说拒收的通知发给**上游任务的主执行人**。而通知是在 `notice-repository` 里**从接收记录派生**的，取的是 `a.task_id` —— 那是**做决定的下游任务**。

实测：上游 = product/ANA，下游 = design/BO 拒收 → 通知 **`role=design member=BO`**。

**拒收人收到了自己刚发出的通知，而成果被拒的人什么都不知道。** 通知的全部意义恰好丢失。

修法是把 join 从 `a.task_id` 换成 `rv.task_id` —— **产出了被拒成果的那个任务**。一行之差，收件人从"决定者"变成"生产者"。

## 顺带补的两处输出缺口

审计还发现两个**字段存了但工具不返回**的问题，都不是业务逻辑错，而是**投影漏了**：

| 缺口 | 后果 |
| --- | --- |
| `task_get` 不返回必交成果与完成标准（MVP-022） | 执行人**看不到自己要交什么、什么算做完** |
| `project_get` 不返回当前正式计划（MVP-003） | 概览**缺了需求点名要有的那一项** |

`requiredResults` / `completionCriteria` 一直在库里、也一直被 hydrate 进记录，**只是没有任何工具把它发出去**。**存了但拿不到，等于没有。**

## 为什么这些能活过 213 个测试

**因为测试只调 service，从不调工具。**

- 归档测试存在，但只测了**资料和方案**两条路径 —— 漏的三条没人测
- `requiredResults` 的**存储**有测试，**输出**没有 —— 投影不是被测对象
- 拒收通知的**存在性**有测试，**收件人**没有
- `project_get` 的返回**没有测试**

**这四类缺口的共同点：被测的是"有没有这个东西"，没测"这个东西对不对、够不够"。**

**这也是本项目第四次遇到同一类问题。** 所以补的不只是修复，还有**一个专门测工具输出的测试文件** `tool-output.test.ts`，让"投影层"从此进入被测范围。

## 验证

| 手段 | 结果 |
| --- | --- |
| 单元测试 | **251 个**（本层新增 13 个） |
| 针对这五个缺口的变异 | **6 项全被抓，0 存活** |
| 归档探针 | 六个写入口**全部被拒**，归档后**新增 0 行** |
| 拒收探针 | 通知收件人 = **product/ANA**（上游），不再是拒收方 |

**变异测试特意在修复之后才做**：测试是**先有修复、后写断言**，这种顺序最可能写成"迁就实现"而不是"约束需求"。**6 项变异全被抓，才说明这些断言真的在卡缺陷。**

## 一处不改：MVP-026 的"必交成果完整性"

审计把"未逐条校验必交成果"报为缺口。**这一条不改**，因为 ADR-0010 已经论证过：必交成果是**自由文本**，题目与文件之间**无法建立可靠对应**，而 MVP 明确**不做质量判断**。

MVP-026 的三项校验**都在**：当前版本、必交成果完整性（**到"交没交"这一层**：说明与自检都非空）、必需输入已接收。

**审计是对的，代码也是对的，分歧在"完整性"能到什么程度。** 已在 ADR-0010 里补了判据，免得下次再被报一遍。

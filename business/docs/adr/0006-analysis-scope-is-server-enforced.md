# 分析只读范围内的内容，范围外根本无法获得

状态：已采用

一次分析**只被给定一组固定版本引用**（`material_id` + `version`）。被分析的内容由**系统按这组引用读出**并交给 Agent，而不是 Agent 自己去仓库里翻。

## 为什么

MVP-013 要求"分析只读取被指定范围内的固定版本资料，不无条件读取项目全部内容；**实际读取范围须可核对**"。

如果做法是"给 Agent 一份清单，让它自己调 `material_read`"，那么这句要求**无法验证**：Agent 手里有通用工具，没有任何东西阻止它读范围外的版本。所谓"可核对"就退化成**信任它的自述**。

**把范围做成工具的输入**，情况就反过来了：范围外的内容**根本没有进入 Agent 的上下文**，因此不依赖自觉。

## 关键认识

这解决了需求描述里的一处表面矛盾。原话要求 Agent"结合**仓库所有材料**不断推进"，而 MVP-013 禁止"无条件读取项目全部内容"。两者可以同时成立：

> **"结合所有材料"指的是看到所有材料的目录，不是读取所有材料的内容。**

目录（名字、用途、版本、大小）**任何时候都可查**——`material_list` 已经实现了这个能力。**内容**才需要逐次显式圈定。**"全部"指的是视野，不是读取量。**

## 排除的方案

**让 Agent 自己调 `material_read`，只记录它读了什么。** 否掉的理由：这记的是**Agent 声称**读了什么，而不是**系统允许**它读什么。两者在验收时不是一回事——MVP-013 要的是后者。

**自动把整个项目塞进上下文。** 否掉：直接违反 MVP-013，且大文件会撑爆上下文。

## 后果

- **"实际读取范围"是系统的记录，不是 Agent 的自述**。读了哪几版、每版是否成功、内容哈希是多少，都在服务端产生。
- **"未覆盖部分"里有一半是客观事实**（点名但读不到、版本不存在），由系统**直接记入**，不由 Agent 申报。**客观事实不该由被考核方自己汇报**——否则会漏掉"声称读了 3 个其实只读了 2 个"这种失败。
- 内容由系统读出，因此**大文件会进入上下文**。MVP 是单人本地使用，接受这一代价；将来可加分片或摘要，但那是**新机制**。
- 分析产出与方案**不做机器引用**：建议由人转写进方案（见 `0005`）。加引用会立刻引出"被引用的建议改版了怎么办"，那是已被裁剪的候选校验链。

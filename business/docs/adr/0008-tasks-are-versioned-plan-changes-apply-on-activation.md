# 任务有版本，且新版本只在方案生效时产生

状态：已采用

正式计划里的任务是一个**有稳定 ID、且自身分版本**的对象。方案里的 `add` / `modify` / `cancel` 是这样作用的：

| 声明 | 作用对象 | 生效时的效果 |
| --- | --- | --- |
| `add` | 无（新建），用方案内的 `ref` 标识 | 创建一个**新任务**，版本 1 |
| `modify` | 已存在任务的 **`task_id`** | 该任务产生**新版本**（版本号 +1） |
| `cancel` | 已存在任务的 **`task_id`** | 该任务终止（**不**删除历史） |

**关键点：`modify` 不立即改任务。** 它只是方案里的一个提议；只有**方案生效时**，任务才产生新版本。

## 为什么

### 为什么 `ref` 不能当任务身份

M4 的 `plan_tasks.ref` **只在一个方案版本内唯一**（主键是 `(plan_id, version, ref)`）。它的用途是让 `depends_on` 能指向**同一份方案里、尚未创建的任务**。

一旦把它当任务 ID，会立刻坏掉：

- 两个方案都定义了 `ref = "t1"` → `modify t1` **无法区分**指的是哪个任务
- Agent 把 ref 从 `t1` 改名成 `spec2` → 就**找不到原任务**了，只能报错或静默当成 `add` 新建，**原任务永远停在那儿没人管**

任务是**独立于方案长期存在**的东西，方案只是**提议变更**的载体。所以任务需要**自己的 ID**。

### 为什么任务要分版本

需求里已经写死了（MVP 需求 L193、L198、MVP-025）：

- 整改路径是「新方案 → 多角色确认 → **新任务版本**」
- 成果版本**必须记录它产生时的任务版本号**，否则整改后**无法回答"当时要求是什么"**
- 验收点：整改后仍能查到旧成果是在**哪一版任务定义**下产生的

所以任务定义必须**可追溯**。若 `modify` 直接覆盖，旧成果记下的任务版本号就**指向一个查不到的东西** —— 这条验收直接不成立。

### 为什么新版本只在生效时产生

这是 M4 门禁的意义所在。

如果 `modify` 一登记就改任务，那么**建议就自动生效了** —— 直接违反 MVP-016（建议不自动成为计划、不自动创建任务）。方案的 `modify` 在收齐确认前**只是一个提议**。

**于是 M5 不需要任何独立的状态机**：任务版本的产生**挂在方案生效这一个动作上**，而 M4 已是唯一入口。这与 MVP-020（整体生效）严丝合缝。

## 排除的方案

**`modify` / `cancel` 指向 `ref`。** 否掉：如上，多方案下无法区分，且改名即丢失目标。

**指向 `(task_id, task_version)`。** 否掉：调用方通常只想说"改这个任务"，逼它报版本号会引出"我报的版本已过时怎么办"——那是**已被裁剪的候选校验链**。版本号由系统递增。

**`add` 也用 `task_id`。** 否掉：新建的任务此刻还没有 ID，让调用方自己发 ID 等于让它决定身份，重复与冲突都要它处理。

**维护两套标识符之外的第三种统一方案。** 否掉：`ref` 存在的唯一理由是"指向同一方案内尚未创建的任务"，而已存在的任务有真 ID —— **两者本就不可能统一**，硬统一会逼出"虚构 ID"这种更糟的设计。

## 后果

- **工具参数里同时存在 `ref` 和 `task_id`，必须写清楚各自用在哪。** 这是最容易出错的地方。
- **已完成任务的定义冻结**：不能再 `modify`，后续变化只能通过新的 `add` 表达。理由见下。
- **`cancel` 一个被下游依赖的任务，在登记时就拒绝**——与成环同样处理（MVP-017：此时尚未收确认，代价最小）。**不做级联取消**：调用方提案 3 个任务、系统悄悄取消 7 个，没人看得见。
- 需要一张任务表、一张任务版本表，以及方案与任务之间的连接（哪个方案的哪一版产生了哪个任务版本）。
- **`task_versions` 只追加，不覆盖。** 出现 `UPDATE task_versions SET ...` 即表示越界。

## 关于"已完成任务冻结"

**未完成**的任务可以被 `modify`，产生新版本。**一旦完成，其定义冻结。**

理由是"当时要求是什么"这个问题：旧成果记录了它产生时的任务版本号，如果那个版本后来被改了，记录就**失真**了。而 MVP 明确要求成果版本**不可变**、整改靠**重新提交**形成新版本。

注意这里的措辞需要准确：拒收后上游走 M4 路径推的是**同一个任务的新版本**（因为这正是"这个任务要整改"的含义），而不是新建任务。所以"冻结"指的是**已完成的那些**。

# 分层：service 承载状态机，sqlite 只负责存取

状态：已采用

代码分五层，依赖只能向下：

```
tool/     薄：参数校验 + 调 service
service/  厚：全部业务规则与事务边界
sqlite/   只做存取，不含业务判断
domain/   类型、错误码、不变量；无 I/O
index.ts  插件装配
```

## 为什么

`DSH-taskboard` 的实测数据表明复杂度**必然**集中在持久化与业务规则：它的 `sqlite/provider.ts` 有 1687 行、`service/index.ts` 有 789 行，两者占了整个代码库约 60%，其余层都很薄。

所以分层的价值不在于"整洁"，而在于**让业务规则能被单独测试**。若 SQL 与状态机缠在一起，"方案生效必须单事务"这类要求就无法独立验证——而那正是 MVP 最贵的失败点。

## 值得记录的取舍

**替代方案**：照搬 taskboard 的"一个大 provider"。它更少文件、上手更快，且在功能上可行。

**为什么仍要拆**：MVP 的 32 条需求天然分成 6 个模块，每个模块的读写自成体系。更重要的是，**单事务跨多表**这个需求（MVP-020 方案生效要同时写方案状态、正式计划、全部任务、输入依赖、确认槽位）在一个巨型 provider 里极难正确表达——事务边界会被淹没在数百个方法中。

## 后果

- **两条纪律必须守住**：`domain/` 不许 import 任何 I/O；`sqlite/` 不许做业务判断（不判断"该不该生效"，只负责存）。违反任一条，事务边界就会失控。
- **实现顺序沿数据流而非需求编号**：domain → sqlite → service（项目→资料→方案→任务→待办→追溯）→ tool → 端到端。
- 每个模块做成**可独立验证的纵切**，不要先把所有表建完再写业务——否则数据模型错了，改动成本会累积。

# 成果挂任务版本，完整性只能校验"交没交"

状态：已采用

M5 成果层引入三个对象：**进展**、**成果版本**、**接收决定**。它们各自挂在哪里，以及"必交成果"能校验到什么程度，是这份 ADR 的内容。

## 挂载关系

| 对象 | 挂在 | 理由 |
| --- | --- | --- |
| 进展 | **任务版本**（`task_id` + `task_version`） | 执行依据是某一版任务定义 |
| 成果版本 | **任务版本**，并记录产生时的版本号 | MVP-025 明文要求 |
| 确认槽位 | 成果版本 | MVP-025 说提交产生一条确认槽位 |
| 接收决定 | **成果版本** × 下游任务 | MVP-027 说下游对"某个具体成果版本"决定 |

**进展挂在任务版本上**，不挂在任务上。原因是同一个：整改前后是两份不同的要求，若进展混在一起，就**无法回答"当时是按什么要求做的"**——与 ADR-0008 保存任务版本的理由完全一致。

## 谁在记录

进展与接收都由**该角色的成员**提交，记录提交者快照（`submitted_by`）。

**这不是鉴权。** 系统不验证调用者是否真的是那个人——与 M4 的确认一致，`submitted_by` 是**快照**，不是凭据。MVP 不做权限（锁定的范围决定）。

## 一次提交 = 一个成果版本

MVP-025 说提交包含"说明、文件**和**自检"，这三样构成**一个**成果版本，不是三个。

**分开交会让"完整成果"无从判断**——MVP-026 要校验必交成果完整性，而完整性是"这一版该交的都在不在"，前提是它们属于同一版。

文件本身落在 M2 已有的存储里（`<项目KEY>/<角色>/...`），成果版本只记**引用 + 哈希**。

## 退回保留成果版本

退回**不产生完成记录**（MVP-026 明文），但**不丢弃成果版本**。

丢弃会让"上一次被退回的是什么"无法查——而**那正是整改的依据**。与 MVP 全局原则一致：成果版本不可变，整改靠**重新提交形成新版本**（L195）。

## 只有被声明的下游才需要接收

MVP-023 要求必需输入**指向具体上游成果版本**，且该成果**已被本任务接收**后，任务才可提交完成。

**没有把某任务列为输入的下游，不该被要求接收。** 否则每个任务完成都要惊动全部下游，而大多数下游并不用它。接收由**下游的角色**决定，拒收**必须给理由**——没有理由的记录没有价值。

## 必交成果只能是文字，完整性只能校验"交没交"

**这是本 ADR 里最需要解释的一条，因为它看起来像功能缺失。**

"必交成果"在 MVP 中用**一个自由文本字段**表达（如"须包含说明文档与自检清单"），系统**只展示，不逐条校验**。

**为什么不做成条目清单**：一旦条目有名字，紧接着就必须回答"**提交的哪个文件对应哪个条目**"。那是**匹配问题**，而 MVP 明确说"只校验完整性，**不做专业质量判断**"（L196）。系统**无法知道**某个文件是不是"需求说明文档"——按文件名猜是错的，让提交者手动挂钩则把负担转嫁给了人。

所以完整性校验**只能做到"有没有交东西"**这一层。这是诚实的边界，不是没做完。

**这一层是怎么落实的**：`submit` 强制 `summary` 与 `selfCheck` **都非空**（`result-service.ts:143-144`），所以**交不出空成果**；`review` 在确认为"完成"时再校验**必需输入已接收**（ADR-0012）。MVP-026 的三项校验——当前版本、必交成果完整性、必需输入已接收——**都在**，其中"完整性"按本 ADR 的边界只到"交没交"。

> **给后来的审查者**：一次审计曾把"未逐条校验必交成果"报为缺口。**那是本条 ADR 有意为之的边界，不是遗漏**。判据是：题目里的自由文本**无法与文件建立可靠对应**，而 MVP 明确**不做质量判断**。要真逐条校验，先得让条目带标识并在提交时显式挂钩。

> 若将来要让系统真的逐条校验，需要**条目带稳定标识 + 提交时显式挂钩**。那是完整版的范围，**不是加个字段就能得到的**。

## 排除的方案

**进展挂在任务上。** 否掉：整改前后混在一起，无法回答"当时的要求是什么"。

**提交一次只交一个文件。** 否掉：说明、文件、自检是同一个成果版本的组成部分。

**退回即丢弃成果。** 否掉：整改失去依据，且与"成果版本不可变"冲突。

**所有下游都要接收。** 否掉：与 MVP-023 矛盾，且会让每个完成动作惊动全体下游。

**必交成果做成带标识的条目清单。** 否掉：立刻引出文件与条目的匹配问题，而 MVP 不做质量判断。

## 后果

- 需要 `progress`、`result_versions`、`result_confirmations`、`acceptances` 四张表。
- `result_versions` **只追加**。出现 `UPDATE result_versions SET ...` 即表示越界。
- **"完成"是确认的结果，不是提交的结果**（MVP-025：提交不等于完成）。任务上的 `completed_at` 只能由确认写入。
- 本层仍然**不实现任务完成后的下游推进**——接收只产生记录与通知（MVP-027）。

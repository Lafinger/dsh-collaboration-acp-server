# 文件存文件系统，按项目/角色分目录

状态：已采用

资料与成果的**二进制内容不入库**，存文件系统；库只存元数据（相对路径、原文件名、大小、哈希、版本号）。

目录结构：

```
<fileRoot>/<项目ID>/<角色>/materials/<资料ID>/v<版本号>__<原文件名>
<fileRoot>/<项目ID>/<角色>/results/<成果ID>/v<版本号>__<原文件名>
```

角色目录用稳定的英文标识（`pm`/`product`/`design`/`scenemodel`/`sceneart`/`data`/`frontend`/`backend`/`ue`），不属于任何角色的资料归 `_shared/`。中文显示名只存在于库里。

## 为什么

**为什么不入库**：需求要处理三维资产与视频（`MAT-009`）。大 BLOB 会让整库膨胀到 GB 级，拖慢备份与查询。`DSH-taskboard` 同样采用"库 + 附件目录"分离。

**为什么按项目 + 角色分**：归档或清理一个项目时可整目录处理，不必扫全库；角色层让"谁的东西"在文件系统里直接可见，与"各角色只关注自己的任务"一致。

**为什么目录用 ID 而非原文件名**：原文件名可能重复、含 `/` 或 `:`、含中文与空格。把它只当显示名，路径就永远安全。

## 值得记录的取舍

**替代方案一：塞进 SQLite BLOB**。优点是把"单一权威"贯彻到底——备份就是拷一个文件，永远不会出现库与文件不同步。

**替代方案二：内容寻址（按哈希分目录）**。优点是天然去重。

**都否掉的理由**：BLOB 撑不住三维资产与视频；哈希寻址让"人肉查看目录"变得不可能——打开文件夹只看到一堆乱码文件名，而 MVP 的使用者就是自己，可读性有实际价值。MVP 没有去重需求，所以内容寻址的优势落空。

**付出的代价**：失去"单一权威"的纯粹性，库与文件可能脱节（如有人手动删了文件）。缓解方式是上传时算哈希并存下来——现在零成本，且是将来加校验的前提。

## 后果

- **备份不再是一个文件，而是"库 + 一个目录"**。`ADR-0001`（SQLite 唯一权威）已明确记录"备份与恢复 MVP 不做"，本条让该缺口的具体代价变大了。
- **不存绝对路径**，只存相对 `fileRoot` 的路径，否则库换机器就失效。
- **删除资料或成果时不真删文件**，只标记失效，与"历史内容只读""归档不删数据"一致。
- **读取时不校验哈希**（大文件会明显变慢），哈希仅在写入时计算。
- **角色成员变更不移动任何文件**。文件位置属于历史事实，与"MVP-004 成员是可变标签、不改写历史"一致。
- **上传链路尚未实测**：ACP 无法直接传文件内容（`promptCapabilities.image/audio/embeddedContext` 均为 `false`），MVP 采用"工具接收绝对路径 → 插件读入落盘"。代价是上传者与插件须能访问同一文件系统。

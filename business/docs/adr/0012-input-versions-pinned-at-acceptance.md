# 0012. 输入版本在接收时钉住，确认完成以已接收的输入为门槛

- 状态：已接受
- 日期：2026-10-11
- 相关：ADR-0008（任务按版本演进）、ADR-0010（成果挂在任务版本上）、MVP-023、MVP-026、MVP-031

## 背景

M7 的目标是回答"当时是谁、依据哪一版、做了什么决定"。而 MVP-031 的验收要点写得更具体：

> 从成果能查到它**生成时实际采用的输入版本**。

**M7 动工前我用探针查了一下，发现这句话当时答不出来。** 两个缺口都是**真实存在**的，不是猜的：

### 缺口 A：输入版本根本没被记下

`task_version_deps` 只存 `depends_on_task_id`：

```
{ task_id: 'c415…', version: 1, depends_on_task_id: '1bb1…', position: 0 }
```

**没有任何地方记录"用的是哪一版成果"**。`result_versions` 的列是 `result_id, version, task_id, task_version, summary, self_check, submitted_by, created_at` —— **没有一列指向输入**。

而 MVP-023 明确要求"任务的**必需输入**须指向**具体上游成果版本**"。

**后果**：上游发了 v1、v2 两版成果，下游接收了 v1 —— **库里查不出"下游用的是哪版"**。

### 缺口 B：确认完成完全不校验必需输入

MVP-026 要求"确认前须校验当前版本、必交成果完整性和**必需输入已接收**"。

探针证明这条**根本没实现**。最极端的情况：

```
b has 1 UNDECIDED acceptance slot(s) open
>>> b COMPLETED with its required input still undecided.
```

**下游连决定都没做（槽位 `outcome: null`），照样确认完成。** 连"没接收"都不拦，更不用说"接收的是旧版"。

## 决定

### 一、输入版本在**接收时**钉住

接收这个动作**本身就隐含了"我用的是这一版"**，所以钉住它**不需要新增任何动作**，也**不引入第二个真相来源**。

否掉的方案：

- **方案登记时钉住版本号**（MVP-023 的字面读法）。否掉：登记时上游成果**可能还不存在**，只能先写"上游任务"，生效时再解——**绕一圈还是回到接收时**。
- **提交成果时由执行人声明**。否掉：多一个必填参数，而且**声明可能与接收决定矛盾**，那时以谁为准？**两个真相来源必然打架。**

### 二、确认完成以"已接收的必需输入"为门槛

有必需输入**尚未被接收**时，`result_review` 拒绝确认。

**关键判断：拒收不算已接收，所以拒收会挡住确认。** 这是**故意的**：

- 上游交付物下游不要 → 下游拒收 → **上游必须整改并重新交付**
- 整改的唯一正规途径是**走方案流程产生新版本**（ADR-0008）
- 所以"被拒收"**本来就意味着上游还没做完**，此时下游不该能确认完成

> **边界**：这条**不会死锁**。要解开，要么下游改为接收，要么上游走方案修订重做。**两条路都不需要新机制。**

**"未被指定输入的任务可直接执行"**（MVP-023 原文）仍然成立：没有必需输入 → 没有门槛。

### 三、追溯按对象查询，返回决定链

回答的是 MVP-031 那句"**依据哪个版本、由谁、何时、作出什么决定**"，所以以对象为入口。

否掉的方案：**一条时间流水**。否掉：它回答的是"什么时候发生了什么"，而"依据哪一版"**还得调用方自己拼**——那正是要避免的。

**所有数据都已经在库里**，这一层不新建业务对象。

## 后果

- **追溯第一次能真正回答"依据哪一版"**，因为那一版**从接收那一刻起就被记下了**。
- **确认完成多了一道真实门槛**：M5 里能过的用例，现在有必需输入时可能过不去。**这是修正，不是回归**——M5 缺的就是这个校验。
- `acceptances` 表要加一列记被接收的成果版本。**拒收也记**（记 rejected），这样"决定过但拒收"与"根本没决定"**可区分**——追溯需要这个区别。
- **M5 的既有测试要重新审视**：那些"确认完成"的用例如果没有先接收输入，**现在应该失败**。这恰好是 Gap B 的回归测试。

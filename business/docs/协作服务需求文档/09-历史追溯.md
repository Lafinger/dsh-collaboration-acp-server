# 09 历史追溯

[返回需求总览](README.md)

## 目的

还原谁依据哪个版本做了什么，区分当时事实与当前状态，让资料、任务、成果和决定可以相互追查。

## 核心需求

| 编号 | 需求 |
| --- | --- |
| TRACE-001 | 资料、需求、方案、计划、任务、成果、反馈和风险处理应保留固定版本，明确当前与历史内容，更新不得覆盖旧事实。 |
| TRACE-002 | 正式决定应记录实际成员、当时角色、时间、结论、理由及固定标准和来源；人工转述应注明记录人，不冒充客户签字或原件内容。 |
| TRACE-003 | 成员可从任务、成果或决定逐层查看输入、成果要求、方案、问题及依据，区分计划要求的输入与实际采用的版本。 |
| TRACE-004 | 任务整改、成果更新、审核拒绝、需求处置和自动废弃应保留前后关系与原因；旧完成记录、决定和输入不被改写。 |
| TRACE-005 | 分析应能追溯触发事项、采用的固定资料、已读范围、遗漏内容、修正过程、校验结果及实际用量；分析成功与业务生效分别记录。 |
| TRACE-006 | 重试、中断与恢复应关联原操作，说明已生效及待恢复的部分，不因重试产生重复完成或分派记录。 |
| TRACE-007 | 历史原件缺失、读取失败或内容不符时应明确提示，不能自动改用最新版，也不能删除对应历史。 |
| TRACE-008 | 历史内容只读；后续处理应定位当前事项并重新核对版本，不能直接通过旧版提交决定。 |
| TRACE-009 | 停权、任命、接任、任务改派、归档和恢复应分别记录操作者、生效时间及责任变化；可还原当时谁有权作决定，不以当前负责人替换历史身份。 |

## 关键规则

- 各项目业务内容按项目组织。任务身份、任务版本与成果版本分别可辨，不要求所有对象共用一个版本号。
- 已完成任务可通过新版重新处理；当前统计反映当前版本，旧版完成事实仍可查。采用新版输入不改写原成果的生成依据；取消任务不计为完成，成功交付与经审核停止项目分别记录。
- 成员退出、负责人更换或角色停用后，历史仍记录实际操作者及当时职责；有效决定不因人员变化自动失效。补审异议的原提出人与现任处理人分别记录，换人不消除异议。
- 完成记录绑定负责人实际核对的成果、自检、任务和输入版本；未纳入的新增材料不混入该记录。风险因终止用途而结束时，保留缺陷、批准决定和影响消除的证据，不改记为已修复。
- 历史可供团队查阅，但不能暴露凭据或敏感管理配置；原文件通过明确的固定版本查看或下载。
- [资料整理](02-仓库整理与资料管理.md)的分类、名称和目录变化同样可追溯，不改变原件身份或旧引用。

## 验收要点

- **TRACE-001～004**：资料更新、任务整改、人员交接后，旧完成记录仍可还原当时成员、标准、输入、成果与决定；人工来源标注清楚。
- **TRACE-003～005**：从下游成果可查到实际接收版本、上游完成、方案审核与分析依据，不把最新版误作历史采用版本。
- **TRACE-006～008**：成功但响应丢失后重试只有一次业务效果；原件缺失有提示；历史记录不能绕过当前版本提交决定。
- **TRACE-009**：停权、换任与提交并发时可查到确定先后；接任者不变成旧决定的操作者，取消、完成、归档及用途终止的风险处理能够区分。

# 08 通知与待办协同

[返回需求总览](README.md)

## 目的

让成员及时找到需要处理的工作，区分必须反馈的待办与纯告知的通知，阅读消息不会误触业务决定。

## 核心需求

| 编号 | 需求 |
| --- | --- |
| NOTICE-001 | 执行、方案审核、成果接收、问题审核、风险处理和澄清等需要反馈的事项进入待办；纯告知进入通知。提醒可关联待办，但不能代替待办。 |
| NOTICE-002 | 成员应能找到自己承担的任务，按项目、角色、类型和状态查找，查看任务版本、责任人及处理条件；可操作范围与实际分派和职责一致。 |
| NOTICE-003 | 通知应有容易发现的入口和准确的个人未读提示，便于区分新消息与已读消息。 |
| NOTICE-004 | 成员应能浏览通知、查看完整详情，并继续查找较早的通知；较多消息不能使历史通知无法到达。 |
| NOTICE-005 | 通知详情成功打开后才记为该接收成员已读；读取失败、只打开列表或他人阅读不改变其阅读状态，重复阅读不重复扣减未读数。 |
| NOTICE-006 | 通知列表、详情与关联操作应支持键盘和不同屏幕尺寸；详情可明确关闭，关闭后能继续原工作。 |
| NOTICE-007 | 通知按实际接收成员保存，可按项目和角色筛选；管理员收到其负责的运行与管理提醒。切换筛选后不得混入旧查询结果。 |
| NOTICE-008 | 通知可定位对应任务、问题或运行记录；旧通知应说明最新状态或历史处置，不引导再次提交过期决定。 |
| NOTICE-009 | 待办和通知随业务结果更新，读取失败可重试；重复请求和中断恢复不重复生成同一提醒，提醒延迟不改变业务处理条件。 |
| NOTICE-010 | 任命后向候任人展示接任确认及完整在办责任；接任生效后更新待办承担者。待交接时显示缺位原因，不把通知或已读当作接任。 |

## 关键规则

- 已读只表示该成员查看过通知，不代表方案同意、成果接收、任务完成、问题解决或风险解除。
- 团队成员可阅读全部项目业务内容；通知筛选与个人待办不构成内容保密边界。执行按分派操作，正式决定由对应角色负责人作出，见[项目与角色管理](01-项目与角色管理.md)。
- 参与者或候任者收到业务提醒不代表获得正式审核权；同一角色不需要所有成员投票。接任生效后，新负责人承接未结决定，包括补审异议的充分性确认；原提出人、历史决定和个人阅读记录不转移或改写。
- 审核反馈拒收可以结束该审核待办，但不能解锁对应执行任务，见[成果交接](05-任务执行与成果交接.md)。
- 通知保留发生时的事实，业务操作始终核对当前版本和资格；阅读历史消息不恢复已失效的待办。按[取消规则](06-需求变化与任务整改.md)结束的待办显示原因，其他下游的义务不受影响。
- 归档后仍可阅读通知并记录个人已读；新业务问题先经团队沟通，由项目管理负责人主动恢复后登记，不在通知中另设恢复申请入口。

## 验收要点

- **NOTICE-001～002**：需要反馈的事项进入正确成员的待办；参与者与负责人可见内容一致，但操作符合分派和职责。
- **NOTICE-003～005**：多名接收成员独立计数；列表浏览、读取失败和他人阅读不误标已读，重复阅读不产生负数。
- **NOTICE-006～008**：键盘与小屏可完整查看并关闭详情；切换筛选无旧结果残留，旧通知能定位当前状态，不能提交过期决定。
- **NOTICE-009**：失败可重试，恢复不重复提醒；通知未显示时也不能绕过审核、接收和完成条件。
- **NOTICE-010**：候任人可核对责任并确认接任，但确认前不能代审；原提出人离职后异议由现任负责人继续处理，不因换人解决，个人已读状态不转移。

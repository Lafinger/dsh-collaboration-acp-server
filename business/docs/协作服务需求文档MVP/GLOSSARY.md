# MVP 语境

协作服务 MVP 是一个无界面的 DeepSeek Harness 插件：它把一个项目的资料、建议、确认、任务和成果存进单一权威库，让 Agent 沿"资料 → 分析 → 多角色确认 → 正式计划 → 任务 → 成果 → 接收"这条链路推进工作。**本语境只描述 MVP**，不代表完整版（见[完整需求文档](../协作服务需求文档/README.md)）的语义。

## 目标接入语境（已确认，尚未实现）

本节记录多成员接入方案已确认的用语；下方现有 MVP 语境仍描述当前实现。其中“会话身份”的自我声明来源将在可信接入身份落地后被替代，不能将两种身份来源混用。

**协作服务**：
供多个成员共同使用的项目管理服务，共享项目业务数据，但各成员的对话上下文相互独立。
_Avoid_：所有成员共用一个会话、成员自己的仓库

**成员接入插件**：
成员在自己的 DSH 中使用协作服务的入口，负责呈现交互，不承担项目业务决策。
_Avoid_：本地项目助手、本地业务决策者

**成员账号**：
经登录确认的成员标识，也是项目角色槽位引用成员的标识；它不是显示姓名，也不是项目角色。
_Avoid_：自报名义、显示名、角色名

**接入身份**：
协作服务确认的当前连接成员，由成员账号确定，不由对话中自报的名字确定。
_Avoid_：服务进程账号、客户端填写的用户名

**会话归属**：
一段对话所属的成员账号；同一成员可以拥有多个独立会话，重新连接不改变原有归属。
_Avoid_：项目角色、当前连接、共用对话

## Language

### 项目与角色

**项目**：
一个顶层容器，持有背景与目标、启用角色、资料、方案、任务和成果。
_Avoid_：工作区、仓库、看板

**项目背景**：
说明项目为什么存在及其所处情境的已确认信息；未知部分保持待补充。
_Avoid_：分析推断、待确认草稿

**项目目标**：
说明项目希望达到什么结果的已确认表述；不等同于方案批准或任务承诺。
_Avoid_：历史交付日期、自动生成计划

**角色**：
九类职责之一（项目管理、产品、设计、场景模型、场景美术、数据、前端、后端、UE端）。**角色完全平级**：任何角色都能创建项目、上传资料、请求分析、登记方案。角色**不是**权限。
_Avoid_：权限、职位、部门、角色标签

**角色成员**：
占据某个角色槽位的人或 Agent（如 `human:alice`、`agent:planner`）。它回答的是「**这个槽位归谁**」，**不是**「现在是谁在说话」——后者是**会话身份**。一个角色最多一名成员；一名成员可同时占据多个角色（**允许一人兼多角色**）。成员是**可变标签**：可随时改，不走交接、不留任职历史。
_Avoid_：用户、账号、负责人、参与者、当前操作者（那是会话身份）

**会话身份**：
当前正在交互的这个人是谁。它回答「**谁在说话**」，与会话绑定：**声明一次，该会话内所有操作以这个名义记录**。

它与**角色成员**是两件事，**必须分开**——因为两者**可以不一致**，而且允许不一致：

| | 回答 | 例子 |
| --- | --- | --- |
| **会话身份** | 谁在说话 | 现在是陈静在跟我交互 |
| **角色成员** | 这个槽位归谁 | pm 这个角色由陈静担任 |

代表某个角色做决定时，**两者必须一致**才允许：陈静是 pm 的成员，才能以 pm 身份确认；她不是 design 的成员，就不能替 design 确认。

**如果不分开**，会出现循环：*"我声明我是 pm，于是我自动成了 pm 的成员"*——任何自封身份都会立刻合法化。
_Avoid_：登录、账号、当前用户（MVP 无身份系统，这只是一个**声明的名义**）

**成员快照**：
记录产生时该角色成员的**当时取值**。它回答"当时是谁做的"；而代表该角色做决定时校验的正是**这个取值**，所以它也回答"当时谁有权做"（见上文「会话身份」）。
_Avoid_：当前成员、身份凭据

**角色空缺**：
某角色槽位没有成员的状态。此时该角色相关的方案**停在等待**并提示，不自动通过、不由其他角色代确认。
_Avoid_：跳过、无人负责

**主执行人**：
承担某项任务的角色成员。
_Avoid_：负责人、经办人

**协作者**：
参与某项任务、但非主执行人的角色成员。
_Avoid_：参与者、组员

### 资料与版本

**资料**：
上传进项目、作为工作输入的原始文件。每份资料归属**一个角色**——上传时该角色；若不属于任何角色则归入共享。
_Avoid_：附件、文档、素材

**资料版本**：
某次上传形成的**不可变**内容。更新资料是追加新版本，不是修改旧版本。
_Avoid_：最新版、当前文件

**固定引用**：
指向某个**具体版本**的引用。读取时按该版本返回，**不会**被自动替换为最新版。
_Avoid_：最新引用、动态引用

**成果**：
一项任务提交时形成的产出，同样不可变。归属**该任务所属的角色**。
_Avoid_：交付物、输出、结果文件

### 分析与方案

**分析**：
Agent 针对一次明确请求，读取**指定范围内**的固定版本资料后形成建议的过程。分析记录必须能回答"看了哪几版、没看什么、哪些是猜的"。
_Avoid_：扫描、全量分析

**分析范围**：
一次分析被允许读取的**固定版本清单**（每项是"某份资料的某一版"）。范围由**调用方给定**，分析只能读到范围内的内容；范围外资料的内容**根本无法获得**，因此无需依赖自觉。
_Avoid_：全部资料、整个仓库

> **边界**：**"结合仓库所有材料"指的是看到所有材料的目录，不是读取所有材料的内容。** 目录（名字、用途、版本、大小）任何时候都可查；**内容**必须逐次显式圈定。这是 MVP-013"不无条件读取项目全部内容"的确切含义。

**未覆盖部分**：
一次分析中**没能覆盖**的：点名但读不到的、读不懂的、依据缺失的。其中**读不到与不存在**属客观事实，由系统直接记入，**不由 Agent 自述**；只有"读不懂"是分析者的判断。
_Avoid_：摘要、省略说明

**推进的发起者**：
发起"下一轮工作"（登记方案、请求分析、催办）的动作**只能由人发起**。Agent 可以**建议**下一轮做什么，但**不能自行启动**。
_Avoid_：自动推进、自动派活、自动循环

> **边界**：MVP **没有调度器**。所谓"内循环"是既有机制的循环：分析产建议 → 人登记方案 → 各角色确认 → 生成任务 → 角色交成果 → 确认完成 → 下游接收 → 产生新待办。**循环不缺机制，缺的是"谁在何时发起下一轮"——答案是人。**

**建议**：
一次分析的产出，**不具约束力**。它不会自动成为计划，也不会自动创建任务。
_Avoid_：结论、决定

**分析的完成**：
分析**只在产出提交后才存在**。中途放弃的一次分析**不留任何记录**——MVP 没有"进行中的分析"这一状态。
_Avoid_：草稿分析、分析任务

> **边界**：记录"进行中"会立刻引出"超时怎么办、要不要清理、如何显示"，而这些**没有任何需求支持**。只有完成的分析才需要回答"看了哪几版"。

**转写**：
把建议变成方案的动作，**由人完成**。建议与方案之间**没有机器引用**——方案不指向某条建议，建议也不知道自己被采纳了。
_Avoid_：引用建议、采纳、同步

**推断**：
分析中未被资料直接支持的内容。必须与"明确需求"和"未决事项"区分，不得被当作承诺。
_Avoid_：假设、推测结论

**来源**：
一条"明确需求"所依据的**具体资料版本**（某份资料的某一版）。**来源必须落在本次分析的范围之内**——范围外的来源等于伪造依据，系统当场拒绝。
_Avoid_：参考、出处

> **边界**：一条声称是"明确需求"的内容，若指不出哪一版资料支持它，**它与推断就没有区别**。所以来源不是可选项，而是"明确"二字的兑现方式。

**未决事项有两个位置，是两样东西**：

- **分析中的未决事项**：本次分析发现的、依据不足以判断的事项。随分析记录一起不可变。
- **方案上的未决事项**：方案自带的一个标记，**随方案走、不随分析走**。它**不阻塞**任何确认，也不因方案生效而消失。

两者**由人转写**，互不引用（见"转写"）。**两处都没有状态机**——没有处理状态、没有负责人、不能被"解决"。
_Avoid_：待办、问题、风险、缺口

**方案**：
一份待确认的工作建议，列明任务的增改取消、每个任务的角色、输入、成果要求与完成标准，以及**需要哪些角色确认**。
_Avoid_：计划、提案、需求文档

**正式计划**：
一份**全部相关角色均已确认**、因而生效的方案。生效是一次整体动作，不产生"部分生效"。
_Avoid_：已批准方案

**未决事项**：
分析识别出的、当前依据不足以判断的事项。它只是方案上的一个标记，**没有处理状态、没有负责人、不能被"解决"**；不因方案生效而消失。
_Avoid_：待办、问题、风险、缺口

> **边界**：完整版有**持续问题**（跨版本跟踪、有分析预算、需多角色确认解决）。MVP **不引入"问题"这一概念**。未决事项若被加上状态机，就等于把已删的 ISSUE 模块加回来——这是有意不做的。

**相关角色**：
一份方案中声明的、必须全部确认才可生效的角色集合。由 Agent 提议，**调用方可在登记方案时修正**；无论谁定，方案都须说明该集合的判定理由。
_Avoid_：审批人、干系人

### 确认与执行

**确认**：
某个**角色**对一份方案或一份成果提交的**同意**或**有理由的拒绝**记录。记录角色、结论、理由、提交者快照与时间。由该角色**自己的成员**提交，一个角色不能替另一个角色确认。
_Avoid_：投票、审批、签字

**方案生效**：
相关角色的确认**全部收齐且均为同意**后，方案整体成为正式计划并生成对应任务的那一刻。任一角色未反馈或拒绝，则不发生。
_Avoid_：通过、批准（易与"单点同意"混淆）

**任务**：
一项有明确角色、主执行人、输入要求、成果要求和完成标准的工作。它**独立于方案长期存在**，有自己的稳定标识；其定义可以变化，每次变化产生一个新的**任务版本**。
_Avoid_：工单、子任务、待办

**任务版本**：
任务定义的一次快照。**只追加、不覆盖**——旧版本永远可查，因为成果版本要记录它是在哪一版任务定义下产生的。
_Avoid_：任务修订、当前任务

**方案中的任务引用（ref）**：
方案**内部**给任务起的临时名字，只在**这一份方案版本内**唯一。它存在的唯一目的，是让依赖能指向**同一份方案里、尚未创建的任务**。它**不是**任务标识——两个方案可以各有一个 `ref="t1"`。
_Avoid_：任务 ID、任务编号

> **边界**：`add` 用 `ref`（新建，此刻还没有标识），`modify` 与 `cancel` 用**任务标识**（改的是已存在的对象）。两套标识符并存是必然的，不是设计缺陷。

**任务定义冻结**：
任务**一旦完成**，其定义不再变化；后续需求只能通过**新的任务**表达。
_Avoid_：锁定、关闭

> **边界**：冻结点在**完成**，不在登记。未完成的任务可以被修改（产生新版本），这正是"退回修改 → 新方案 → 新任务版本"这条路径所需要的。冻结的理由是：旧成果记录了它产生时的任务版本，若那一版后来被改掉，"当时要求是什么"就失真了。

**任务定义**：
任务版本里"要求什么"的那部分：角色、工作要求、**必需输入**。它随任务版本一起冻结。
_Avoid_：任务内容

**任务的人员归属**：
任务由**哪个角色**承担。**它不是任务版本的一部分**——具体由谁执行，是"该角色当前的成员"，是个**查询**而非快照；存下来会在换人时失真。
_Avoid_：主执行人字段、负责人

> **边界**：MVP-022 要求任务展示"主执行人（该角色成员）"。这是**由角色与项目成员推导出来的**，不是任务上存的字段。协作者同理。

**进展**：
任务执行过程中的过程记录，可多次追加。保存进展**不**完成任务，也不驱动任何下游。
_Avoid_：进度汇报、完成

**提交成果**：
主执行人把说明、文件和自检一并提交，形成**不可变成果版本**的动作。提交**不**完成任务。
_Avoid_：交付、完成

**确认完成**：
角色负责人核对已提交的固定成果版本后，判定该任务达成其完成标准的决定。它产生"完成"事实，与"提交"是两个不同事件。
_Avoid_：提交、验收（"验收"易与下游接收混淆）

**接收**：
下游任务对某个具体成果版本作出"可供我使用"的决定，是**独立于上游完成**的动作。每个下游任务分别决定。
_Avoid_：验收、确认完成、采用

**拒收**：
下游任务判定某成果版本不满足其输入要求的决定。它**不**撤销上游的完成事实，也**不**影响其他下游的接收。MVP 中拒收**只产生一条记录和一条通知**，不自动触发任何后续流程——上游若认为需要整改，须自己按"新方案 → 多角色确认 → 新任务版本"推进。
_Avoid_：退回、驳回、问题

**退回修改**：
角色负责人判定当前提交尚不合格、任务保持未完成的决定。它区别于拒收：退回不产生完成记录，拒收是下游对已完成成果的判断。
_Avoid_：拒收、驳回

> **边界（实现补充）**：退回**不丢弃成果版本**。被退回的那一版正是整改的依据；丢弃它，"上次哪里不行"就查不到了。整改靠**重新提交形成新版本**。

**必交成果**：
任务定义中说明"须交出什么"的**文字**，与完成标准一样属于任务版本，改了就该产生新任务版本。MVP 中系统**只展示，不逐条校验**。
_Avoid_：交付清单、验收标准、质量要求

> **边界**：为什么不做成带标识的条目清单——一旦条目有名字，就必须回答"哪个文件对应哪个条目"，那是**匹配问题**，而 MVP 明确"只校验完整性，不做专业质量判断"。所以完整性在 MVP 中**只能是"交了东西"**。这是刻意划定的边界，不是未完成项。

**接收槽位**：
为某个成果版本、给**声明了该任务为输入**的下游任务开出的待决位置。开槽位**不等于**接收：开完仍是未决。
_Avoid_：待办、通知

> **边界**：只有 `depends_on` 声明过的下游才有槽位。给全项目每个任务开槽位会让**每次完成都惊动全体下游**，而大多数下游并不消费该产出。

### 协同与追溯

**待办**：
归属到**某个角色**、需要该角色**反馈**的事项：方案确认、成果确认、成果接收。
_Avoid_：任务、通知、控制任务（"控制任务"是完整版用词，还含问题审核与风险处理，MVP 不沿用）

**通知**：
仅**告知**的信息，不需要反馈。它与待办不得混淆：阅读通知不产生任何业务决定。
_Avoid_：待办、提醒

**已读**：
某个接收者查看过某条待办或通知的记录。它**只表示看过**，不代表同意、完成、接收或解决。
_Avoid_：已处理、已确认

**追溯**：
从任一对象出发，查清它"依据哪个版本、由谁、何时、作出什么决定"的能力。追溯须区分**当前版本**与**历史版本**。
_Avoid_：日志、审计

**消费的输入版本**：
下游任务在**接收**上游成果时钉住的那一个具体成果版本。它是"这份成果当时依据的是哪一版"的答案，**在接收那一刻确定**。

与**必需输入**的区别：必需输入说的是"这个任务**需要**谁的产出"，是一个**任务**；消费的输入版本说的是"它**实际用了**哪一版"，是一个**具体的成果版本**。同一份必需输入可能有多版成果，只有被接收的那一版算消费。
_Avoid_：依赖版本、上游版本（说不清是任务还是成果）

**未决定不等于已拒收**：
槽位还开着，说明下游**还没表态**；已拒收，说明下游**明确不要**。两者都会挡住完工，但**原因不同**，追溯必须能分辨。
_Avoid_：待处理、未完成（说不清是没表态还是已否决）

### 人与 Agent 的分工

本组术语只描述**人怎么跟它打交道**，不描述项目里发生什么。

**自主调用**：
Agent **自己决定**用哪个工具、调几次来落实人说的事。人只需说出想做什么，**不需要**先解锁、授权或说出特定词语。
_Avoid_：自动执行、自动推进（那说的是"要不要推进项目"，是另一回事）

**无感**：
本语境下特指**"不用关键词"**这一件事，范围**仅此而已**。人仍然要开口说「建个项目」「看看待办」——**无感的是不用念咒语，不是不用说话**。

它**不**承诺：模型主动提醒下一步（需要新的触发时机），也**不**承诺模型自行推进项目（需要调度器，MVP 不做）。凡超出这个范围的要求，都是**另一个需求**，不要用它来涵盖。
_Avoid_：全自动、无人值守、主动服务（都超出了它实际承诺的范围）

**推进的发起者**：
决定"**这个项目要不要往下走**"的一方，在 MVP 里**是人**（见 [ADR-0005](../adr/0005-no-scheduler-human-initiates.md)）。

它与**自主调用**是两件事，不能混：

| | 谁决定 | 需要授权吗 |
| --- | --- | --- |
| **要不要推进这个项目** | 人 | 人开口即是发起 |
| **这一次用哪个工具去推进** | Agent | **不需要**，完全自主 |

_Avoid_：自动流转、Agent 自行推进

**触发词 / 咒语**：
要求人**先说出特定词语**才允许调用工具的机制。**MVP 明确不做**（MVP-033）。
_Avoid_：唤醒词、口令（除非正是在指这个被否决的机制）

**只读模式**：
"这一轮只准查、不准改"的限制。它**不同于**触发词：触发词是全开或全关，**拦不住"想查却顺手改了"**。MVP **未实现**，属独立需求。

## 本语境刻意使用的说法

| 用 | 不用 | 原因 |
| --- | --- | --- |
| 角色 | 角色标签 / 负责人 | 角色有成员且完全平级；"标签"掩盖成员归属，"负责人"暗示层级与任职 |
| 角色成员 | 用户 / 账号 / 成员 | 成员是可变标签，不是需要管理的身份实体 |
| 确认 | 审核 / 审批 | "审核"在完整版含审阅全案与代表权含义，MVP 只有"同意/拒绝"记录 |
| 方案生效 | 方案通过 | "通过"易被理解为单点同意；生效强调"全部角色收齐" |
| 接收 | 验收 | "验收"同时被任务完成与下游接收使用，是完整版主要混淆源 |
| 待办 | 控制任务 | 完整版"控制任务"还含问题审核与风险处理；MVP 不含，沿用会误导 |
| 未决事项 | 问题 / 风险 | MVP 不引入"问题"概念；加状态机等于把已删的 ISSUE 模块加回来 |
| 固定引用 | 引用 / 链接 | 强调绑定具体版本、不被最新版替换 |
| 成员快照 | 当前成员 | 快照回答"当时是谁做的"，不回答"现在是谁" |
| 会话身份 | 用户 / 账号 / 登录 | MVP 无身份系统；它只是一个**声明的名义**，且与"槽位归谁"是两回事 |
| 角色成员 | 当前操作者 | 前者是槽位归属（长期），后者是当下谁在说话（会话内） |
| 自主调用 | 自动推进 | 前者说的是 Agent 自己选工具（预期行为）；后者说的是 Agent 自己决定推进项目（MVP 不做） |
| 会话内称呼 | 触发词 / 暗号 | 叫它什么都行，**与工具能否调用无关**；"触发词"暗示有一道需要解锁的门 |
| 只读模式 | 触发词 | 想防"顺手改数据"，要的是只读限制，不是先解锁再全放开 |

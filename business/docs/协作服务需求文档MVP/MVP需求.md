# 协作服务 MVP 需求

[返回 MVP 总览](README.md) ｜ [裁剪对照表](裁剪对照表.md)

本文件定义 MVP 应具备的能力与可观察的验收条件。**不表示功能已经实现。**

- MVP 需求编号为 **MVP-001 ~ MVP-033**，与完整版的 115 条对应关系见[裁剪对照表](裁剪对照表.md)。
- 不规定内部实现，但**前提是**：DSH 插件形态、SQLite 权威、无界面、无权限（见 [README](README.md)）。
- 原文档中"由角色负责人代表角色审核"的**权限**语义在 MVP 中不成立：不做任命、接任、停用、代表权，也不做任何**认证**（没有登录、账号、凭据）。但 MVP **要求成员资格成立**——代表某个角色做决定时，会话声明的身份必须是该角色槽位的成员。**不认证不等于谁都能代表任何角色**，两者的区分见[裁剪对照表](裁剪对照表.md)的变更记录。

## M1 项目与角色标签

### 目的

建立项目容器，标明这项工作涉及哪些角色，让人和 Agent 知道该找谁确认。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-001 | 可创建项目，登记名称、简短标识和背景目标；未提供的背景目标留空并标为待补充，不编造。 |
| MVP-002 | 项目可启用若干**角色**（九类之一）；每个角色有一个**成员槽位**，可为空。 |
| MVP-003 | 可查询项目列表与单个项目概览（背景、目标、启用角色及其成员、当前正式计划）。 |
| MVP-004 | 角色成员是一个**可变标签**（如 `human:alice`、`agent:planner`）：可随时改，不走交接流程、不做接任确认、不保留任职历史。记录须保存**当时的成员快照**，以便追溯"当时是谁做的"。代表该角色做决定时，**会话声明的身份必须与该角色当时的成员一致**，否则拒绝（见 MVP-019）。 |
| MVP-005 | 项目可归档；归档后业务只读，不再接受新的资料、方案、任务或成果写入。 |

### 关键规则

- **九类角色**：项目管理、产品、设计、场景模型、场景美术、数据、前端、后端、UE端。
- **一角色一成员**：一个角色最多一名成员；一名成员可同时占据多个角色。九角色**完全平级**——任何角色都能创建项目、上传资料、请求分析、登记方案。
- **唯一的硬约束**：**一个角色不能替另一个角色确认**。这是门禁完整性的保证。
- **同一人占多角色时，确认须分别提交**：不允许"一次确认顶多个角色"，否则"全部相关角色同意"会被架空。系统按角色分别校验成员资格，因此同一人兼任多个角色时须**逐个角色提交**。
- **角色空缺时方案卡住**：某相关角色没有成员时，方案停在等待并提示"角色空缺"，不由其他角色代确认、不自动跳过。
- 归档不删除数据，只是停止写入。

### 验收要点

- **MVP-001**：创建项目时未填的背景目标显示为待补充，不被自动填充。
- **MVP-002**：只能使用九类角色；可为角色设置或清空成员，无需任何权限。
- **MVP-003**：可查到项目概览、各角色成员及其当前正式计划。
- **MVP-004**：改成员后，历史记录仍显示**当时的成员快照**；改成员不产生任何交接或审批要求。
- **MVP-005**：归档后写入被拒绝并说明原因；已有数据仍可读。

## M2 资料与固定版本

### 目的

把原始资料放进项目并**固定下来**，让后续分析和决定都能指向"当时那一版"。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-006 | 可向项目上传资料，登记项目、原文件名、用途和提交者。 |
| MVP-007 | 每次上传形成**不可变版本**；同一资料更新产生新版本，旧版本内容与引用不被覆盖。 |
| MVP-008 | 可列出项目资料及其版本，读取指定版本的内容。 |
| MVP-009 | 引用资料时必须绑定**具体版本**，读取时按该版本返回；不得自动替换为最新版。 |
| MVP-010 | 同项目下同名资料的重复上传须明确处理：默认形成新版本，不静默覆盖。 |
| MVP-011 | 无法解析或读取的资料须说明原因，并保留原件可读；不显示为空文件。 |

### 关键规则

- **不可变**是本节唯一硬约束：任何"更新"都是**追加新版本**，不是修改旧版本。
- MVP 只做**平坦的资料列表 + 版本**，不做目录树、不做逻辑目录整理、不做整理审批。
- 资料与"任务成果"是不同对象：资料是输入，成果是任务的产出（见 [M5](#m5-任务执行与成果交接)）。
- 上传不推进任何流程，也不完成任何任务。

### 验收要点

- **MVP-006 ~ MVP-007**：两次上传同名文件后能查到两个版本，旧版本内容不变。
- **MVP-008 ~ MVP-009**：按固定版本号读取得到当时的原文；资料更新后，旧引用仍返回旧版本。
- **MVP-010**：重复上传被明确处理，不出现静默覆盖。
- **MVP-011**：读取失败给出原因，且原件仍可获取。

## M3 Agent 分析与建议

### 目的

让 Agent 基于**固定版本的资料**形成有依据、可核对、可被确认的建议，并诚实说明未知内容。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-012 | 可请求一次分析，记录触发原因（**必填**）、分析范围、所依据的资料（含版本号）和时间。 |
| MVP-013 | 分析只读取**被指定范围**内的固定版本资料，不无条件读取项目全部内容；实际读取范围须可核对。范围由**系统强制执行**：范围外资料的内容**根本无法获得**。 |
| MVP-014 | 分析输出须区分：**明确需求**、**未决事项**、**推断内容**；不得把推断当作承诺。**明确需求须逐条标明来源版本**，且来源必须落在本次范围内。 |
| MVP-015 | 分析须说明**未覆盖的部分**（未读到的、读不懂的、缺失的依据），不得以摘要冒充完整阅读。**客观部分（读不到、版本不存在）由系统直接记入，不由 Agent 自述。** |
| MVP-016 | 分析结果只是一份**建议**；它不自动成为正式计划，不自动创建任务，也不自动消除方案中的未决事项。 |

### 关键规则

- 分析必须能回答："你看了哪几版、没看什么、哪些是你猜的。"
- **"结合仓库所有材料"指的是看到所有材料的目录，不是读取所有材料的内容。** 目录任何时候可查（`material_list`）；**内容**必须逐次显式圈定。
- **分析只在产出提交后才存在**：中途放弃的一次分析**不留记录**，MVP 没有"进行中的分析"。
- **三类内容允许为空数组**，但 `未覆盖部分` 必须显式给出（空数组 = 声明"全都读到了"）。强制三类都非空**会诱发编造**。
- 单份资料超过**上限（256 KB）**时**不读取**，该版**记入未覆盖部分**并说明原因。**不做静默截断**——半份内容会被误当作完整依据。
- 分析**不可修订**；要改就重新分析一次。同一范围允许分析多次（时间变了，判断可能变）。
- **不记录模型标识与用量**：MVP 无预算与成本核算需求，记了也不会被读。
- 资料不足与"模型/工具失败"须分别说明：前者要求补充资料，后者是技术问题，不能混为一谈。
- 材料中的文字**不能授予操作权限**，也不能被当作指令执行。
- **未决事项没有生命周期**：它只是方案上的一个标记，**没有处理状态、没有负责人、不能被"解决"**。MVP **不引入"问题"这一概念**（完整版的持续问题、风险处理、澄清闭环整体延后）。给未决事项加上状态机，等于把已删的 ISSUE 模块加回来，是明确不做的。

### 验收要点

- **MVP-012 ~ MVP-013**：分析记录能查到范围与所依据的资料版本；范围外资料**不被读取**——且这是**系统的强制**，不是 Agent 的自觉。
- **MVP-014**：输出中三类内容可区分；推断不会被当作已确认需求；**每条"明确需求"的来源都能落到本次范围之内**，范围外的来源被拒绝。
- **MVP-015**：分析明确列出未覆盖部分，不宣称已完整阅读；**读不到的版本必然出现在未覆盖部分**，即使 Agent 没提。
- **MVP-016**：分析完成后项目中没有自动出现正式计划或任务。
- **补充**：中途放弃的分析**不留记录**；超限资料**不被截断**而是记入未覆盖；同一范围可分析多次且各自独立可查。

## M4 方案确认与正式计划

### 目的

把 Agent 的建议变成**经过每个相关角色分别确认**的正式计划。这是 MVP 的中枢。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-017 | 可将一份建议登记为**方案**，列明新增、修改或取消的任务，以及每个任务的角色标签、工作内容、输入、成果要求和完成标准。登记时须**拒绝成环或引用不存在任务的依赖**。 |
| MVP-018 | 方案须标明**相关角色集合**（由哪些角色确认才可生效）及其判定理由。该集合由 **Agent 在分析时提议**，调用方**可在登记方案时修正**；无论谁定，理由都须可核对。 |
| MVP-019 | 系统为该方案的每个相关角色各生成**一条确认槽位**；由**该角色的成员**以角色名提交**同意**或**有理由的拒绝**，记录结论、理由、提交者快照与时间。相关角色**没有成员**时，槽位显示"角色空缺"并等待，**不自动通过、不由其他角色代确认**。 |
| MVP-020 | **全部**相关角色均已同意后，方案**整体生效**成为正式计划并生成对应任务；任一角色未反馈或拒绝，方案不生效。**生效须在单个事务内完成**（写方案状态、写正式计划、创建全部任务、建立输入依赖、关闭已完成的确认槽位），不得出现半生效。 |
| MVP-021 | 方案可修订：**无论是否已收到部分确认都可修改**；修改后形成**新版本**，已收到的确认**全部作废**，须**重新**收齐全部相关角色确认。作废的确认**保留并标记失效**（记录作废原因与时间），不物理删除。旧版本的内容与确认历史保留可查。 |

### 关键规则

- **这是 MVP 唯一的门禁**：没有"每个相关角色各一次确认"，方案不得生效。
- 确认按**角色**记录，且**必须由该角色槽位的成员提交**——会话声明的身份与该角色成员不一致时**拒绝**。但这**不是**权限或安全机制：MVP 不做认证，身份是**会话内自我声明**的（见 MVP-004 与术语表"会话身份"）。
- **同一人占多角色时须分别提交确认**：不允许一次确认顶多个角色，否则"全部相关角色同意"会被架空。
- 拒绝必须带理由；**不因超时自动通过**，不因已读自动通过。
- 方案生效 ≠ 其中的任务已完成，也 ≠ 未决事项已消除。
- **允许在收齐前修订**：产品已同意、设计未表态时也可以改方案；改动使已收到的确认全部作废。禁止修改会让人卡在"收齐前不敢动"，反而更糟。
- **循环依赖在登记时就拒绝**，不等任务执行时才发现——此时尚未收确认，代价最小。
- MVP 不做"遗漏角色异议"、"推断纠正"、"重评预算"等进阶机制（见[裁剪对照表](裁剪对照表.md)）。

### 验收要点

- **MVP-017**：方案内容与相关角色集合及其理由均可查；调用方对相关角色的修正被记录；**成环或引用不存在任务的方案被拒绝**。
- **MVP-019**：每个相关角色各有独立确认槽位；确认记录含角色、结论、理由与提交者快照；**角色空缺时方案停在等待并提示**。
- **MVP-020**：缺任一角色确认时方案**不生效**且不生成任务；全部同意后**一次性**生效并生成任务；模拟中途失败时不留下半生效状态。
- **MVP-021**：含部分确认的方案被修改后，旧确认**标记为失效但保留可查**，必须重新收齐。

## M5 任务执行与成果交接

### 目的

让方案变成实际推进：有人做、有成果、有人确认完成、下游明确接收。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-022 | 任务展示角色、主执行人（该角色成员）、协作者、工作要求、输入、必交成果、完成标准和当前**任务版本**。 |
| MVP-023 | 任务的**必需输入**须指向具体上游成果版本，且该成果已被本任务**接收**后，任务才可提交完成；未被指定输入的任务可直接执行。 |
| MVP-024 | 可多次保存**进展**（文字或文件）；保存进展**不**完成任务，也不驱动任何下游。 |
| MVP-025 | 主执行人可**提交成果**：包含说明、文件和自检，形成**不可变的成果版本**并生成一条确认槽位。**成果版本须记录它产生时的任务版本号**。 |
| MVP-026 | 该**角色**可**确认完成**或**退回修改**；确认前须校验当前版本、必交成果完整性和必需输入已接收，不足则拒绝并说明原因。退回不产生完成记录。 |
| MVP-027 | 确认完成后，下游任务可对该成果版本作出**接收**或**拒收**决定；接收是独立决定，不由上游完成自动触发。**拒收只产生一条记录和一条通知**（通知上游任务的主执行人），不自动触发任何后续流程。 |

### 关键规则

- **提交 ≠ 完成**：主执行人提交只产生待确认的成果版本；只有确认完成才产生"完成"事实。
- **完成 ≠ 接收**：上游完成不代表下游已接受；每个下游任务**分别**决定接收。
- **保存进展 ≠ 完成**：进展是过程记录，不能替代任何决定。
- **任务版本与成果版本是两个独立序列**：任务定义变化产生新的**任务版本**；每次提交产生新的**成果版本**。成果版本必须记住它是在哪一版任务定义下产生的，否则整改后无法回答"当时要求是什么"。
- **任务有稳定标识，独立于方案存在**：方案里的 `modify` / `cancel` 必须指定**任务标识**（不是方案内的 `ref`）；`add` 用方案内的 `ref`，因为它此刻还没有标识。**两套标识符并存是必然的**，工具参数须写清各自用在哪。
- **任务的新版本只在方案生效时产生**：方案里的 `modify` 在收齐确认前**只是提议**，不立即改任务。若它一登记就生效，等于绕过门禁（违反 MVP-016）。
- **任务一旦完成，定义冻结**：已完成任务不可再被修改，后续需求只能通过**新的任务**表达。理由是旧成果记录了它产生时的任务版本，改掉那一版会让"当时要求是什么"失真。
- **`cancel` 一个被下游依赖的任务，在登记时就拒绝**（与成环同样处理，此时尚未收确认，代价最小）。**不做级联取消**——调用方提案 3 个任务、系统悄悄取消 7 个，没人看得见。
- **同一角色可分饰确认者与执行者**：若某角色既确认方案、又承担该方案下的任务，这是**两件独立的事**，分开记录（见 [ADR-0004](docs/adr/0004-one-member-per-role-flat.md)）。MVP 不做"自己不能审自己"的制衡。
- 成果版本**不可变**；整改通过重新提交形成**新版本**，旧完成记录与旧成果保留。
- MVP 只校验成果的**完整性**（该交的有没有交、输入是否已接收），**不做专业质量判断**。
- 等待接收期间可保存进展，但不产生完成和新交接。
- **拒收不是状态机的起点**：上游若认为需要整改，须**自己**走"新方案 → 多角色确认 → 新任务版本"这条 M4 路径。MVP 不提供"上游整改/说明无需修改/请求澄清"的自动分支（完整版 ISSUE-003 整体延后）。

### 验收要点

- **MVP-022 ~ MVP-023**：必需输入未接收时，提交完成被拒绝并说明原因。
- **MVP-024**：多次保存进展后任务仍未完成，且没有下游待办产生。
- **MVP-025 ~ MVP-026**：提交本身不完成任务；缺必交成果或输入未接收时确认被拒绝；确认成功后产生**一次**完成事实与必要待办。
- **MVP-027**：一个下游接收不影响其他下游；拒收不撤销上游完成事实，成果版本仍可查；**拒收后项目中没有自动出现新方案、新任务或"问题"对象**。
- **补充（任务身份与版本）**：方案的 `modify` 在生效前**不改动任务**；生效后该任务产生**新版本**且旧版本仍可查；已完成任务被 `modify` 时拒绝；`cancel` 被依赖的任务在**登记时**被拒绝。
- **任务版本与成果版本**：任务定义整改后，仍能查到旧成果是在**哪一版任务定义**下产生的。

## M6 通知与待办

### 目的

让人和调用方知道**下一步要处理什么**，并区分"必须反馈"和"只是告知"。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-028 | 需要反馈的事项（方案确认、成果确认、成果接收）进入**待办**；纯告知信息进入**通知**；两者不得混淆。 |
| MVP-029 | 待办须归属到**具体角色及其成员**，并指向对应对象（方案/任务/成果）及其版本；**成员可查到"自己角色"名下的待办**，可按角色、类型和状态筛选。 |
| MVP-030 | **已读只表示看过**，不代表同意、完成、接收或解决；已读**按角色槽位记录**；重复读取不重复计数，未读数量不为负。 |

### 关键规则

- 阅读通知**不产生**任何业务决定。
- 已交付的待办不因读取而消失；完成待办只能通过提交对应决定。
- **待办归属角色，不归属"所有人"**：某角色的待办只有该角色需要处理，这与"各角色只关注自己的任务"一致。
- **角色空缺时的待办**：槽位存在但无成员，待办仍可查询并显示"角色空缺"，但不产生"未读"提示。
- MVP 不做投递隔离（无权限模型，所有记录同库可见）：**可查询不等于有资格处理**——但 MVP 也不校验资格（见 [ADR-0004](docs/adr/0004-one-member-per-role-flat.md)）。

### 验收要点

- **MVP-028**：方案确认、成果确认、成果接收各自产生待办；纯提示不产生待办。
- **MVP-029**：待办能定位到具体角色、对象及版本；按角色筛选时不混入其他角色的待办。
- **MVP-030**：标记已读不改变业务状态；重复标记不产生重复计数；角色空缺的待办不产生未读。

## M7 追溯与端到端验收

### 目的

回答"当时是谁、依据哪一版、做了什么决定"，并用一次完整演练证明主链路成立。

### 核心需求

| 编号 | 需求 |
| --- | --- |
| MVP-031 | 资料、方案、任务、成果和决定均保留固定版本与操作记录（谁、何时、依据哪个版本、结论与理由），更新不覆盖历史。 |
| MVP-032 | 在空库上完成端到端演练：建项目 → 上传资料 → 分析并登记方案 → 相关角色各确认一次 → 方案生效生成任务 → 提交成果 → 确认完成 → 下游接收 → 全程可追溯。任一环节缺失即不算完成。演练经 ACP 会话驱动，不使用界面。 |

### 关键规则

- 追溯须区分**当前版本**与**历史版本**；从成果能查到它生成时实际采用的输入版本。
- 历史内容只读；对旧版本的操作用新版本进行，不改写历史。
- 已归档项目的历史仍可查。
- 演练**分两段执行**（便于定位问题）：先验不依赖模型的状态机步骤（上传、方案登记、按角色确认、方案生效、提交、确认完成、接收、追溯），再验依赖 Agent 的步骤（分析、方案生成）。凭据已核实可用（见[事实核查](docs/验证/DSH-ACP-事实核查.md)），故两段都属必做。

### 验收要点

- **MVP-031**：任取一条决定，能查到提交者、时间、依据版本和理由；资料更新后旧引用与旧决定不变。
- **MVP-032**：演练全程无需界面；每一步的结果都能通过查询独立核实；**断链即失败**。

## M8 交互原则

### 目的

M1~M7 规定的是**项目里发生什么**。M8 规定的是**人怎么跟它打交道** —— 只此一条，但它约束前面每一个模块的调用方式。

### 需求

| 编号 | 需求 |
| --- | --- |
| MVP-033 | Agent **自主选择并调用**工作台工具，人用自然语言表达意图即可。**不得要求用户输入触发词、咒语或任何形式的显式授权**才能调用工具。 |

### 关键规则

- **"自主调用"指模型自己决定用哪个工具**，不是指它可以自己决定"要不要推进项目"。推进仍由人发起（ADR-0005），两者不矛盾：**人开口，模型选工具。**
- **"无感"的准确定义（用户原话）**：**"模型会自动调用相关工具，不需要关键词。"** 它说的是**不用关键词**这一件事，**仅此而已**。
  - **它不承诺**：模型主动提醒你下一步该干嘛（那需要新的触发时机，属另一需求）。
  - **它不承诺**：模型自行推进项目（那需要调度器，ADR-0005 已排除）。
  - 换句话说，人依然要开口说「建个项目」「看看待办」——**无感的是"不用念咒语"，不是"不用说话"。**
- 因此**明确不做**：工具门禁、会话内触发词、按轮次锁定的调用授权。
- 这条需求**否定的是"授权"这一层**，不是"人在场"。人始终在场并发起每一轮。

### 验收要点

- **MVP-033**：走完 MVP-032 的整条演练链路，**全程没有任何一步需要用户输入特殊词**才能让工具被调用；若某个工具必须靠触发词才会执行，即不通过。

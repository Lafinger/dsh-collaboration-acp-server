# 一角色一成员，全角色平级

状态：已采用；取代 [ADR-0002](0002-roles-are-tags-not-permissions.md)

> **修订（2026-10-11）**：下文「边界一」中"**不回答'当时谁有权做'**"、「关于同一人占多角色」中"**实现上不校验身份**"、「后果」中"**后续加身份校验**"与"**仍不能用于多人真实协作**"四处**已不再成立**。
> 起因：转向多成员客户端接入（见 [ACP 独立运行时方案](../../ACP独立运行时方案.md)）后，"不校验身份"的后果是**任何成员都能以任何角色名义确认**。
> 现改为**校验成员资格**——会话声明的身份必须是该角色槽位的成员，否则拒绝。这**仍不是权限体系**（认证、任命、接任、停用、代表权照旧不做）。
> 理由与影响见[裁剪对照表](../../裁剪对照表.md)的变更记录。以下正文保留当时的推理，**不作现行依据**。

MVP 为九类专业角色各设**一个成员槽位**（可空）。一个角色最多有一名成员，一名成员可同时占据多个角色。**九角色完全平级**：任何角色都能创建项目、上传资料、请求分析、登记方案，不存在任免链、没有"负责人 vs 参与者"的层级。

唯一的硬约束：**一个角色不能替另一个角色确认**。这是"每个角色只关注自己的任务"的机制保证，也是方案门禁（"全部相关角色各确认一次"）的完整性所系。

## 为什么取代 ADR-0002

ADR-0002 把角色压缩成**纯标签**，导致 `NOTICE-002`（成员应能找到**自己承担的**任务）在 MVP 中**无法实现**，只能降级为"状态可查询"；同时"待办给谁"变成悬空问题。

改为"一角色一成员"后：待办直接归属该角色；"各角色只关注自己的任务"成为可实现的语义。这比纯标签**更贴近原文档**——原 `PRJ-007` 本就写着"一人可兼多角"，`README` 也写着"一个成员可承担多个角色"。

本决策**不是**恢复权限：被删的 `PRJ-009/011/012/013/014`（任命、接任确认、停权、交接清单、管理员资格交接）仍然不做。

## 三条边界（这是本 ADR 的核心）

**边界一：成员是可变标签，不是需要管理的实体。**
成员可以随时改一个字符串，**不走交接流程、不做接任确认、不保留任职历史**。历史记录保存**当时的字符串快照**，因此能还原"当时是谁做的"，但**不回答"当时谁有权做"**。
这条边界是为了防止权限从后门回流：一旦成员成为需要管理的实体，"能不能停用""停用后历史怎么办""谁能加成员"会立刻出现，而那正是被删掉的 5 条需求。

**边界二：同一角色可同时是确认者与执行者，但分开记账。**
一份方案的相关角色可能既确认该方案、又承担其中某个任务。MVP **不做"负责人审、参与者干"的分离**（那是权限设计）。改为：`确认记录` 与 `任务提交` 是**两个不同对象**，即使提交者是同一角色，也是两件事，追溯时不会混淆。
代价：失去"自己不能审自己"的外部制衡——这属权限范畴，MVP 明确不做。

**边界三：角色空缺时方案卡住，不自动通过。**
某相关角色没有落实成员时，方案**停在等待并明确提示"角色空缺"**，不由其他角色代确认、不自动跳过。
理由：若允许空缺自动跳过，"相关角色"这个门禁可以被**人为绕过**（把难缠的角色留空即可），门禁就失去意义。

## 关于同一人占多角色

**确认必须分别做**：一个人占产品+设计时，要提交两条确认。这保留了原文档的关键规则"一人兼任多个角色时，仍须分别完成各角色审核"。
实现上**不校验身份**（同 ADR-0002 的技术立场），所以人只是多提交一次而已；但若允许"一次确认顶多个角色"，`MVP-020` 的"全部相关角色同意"就会被架空。

## 后果

- **确认记录以角色为键**，不是以人为键。这使 ADR-0002 预留的数据形状（后续加身份校验）依然成立。
- **仍不能用于多人真实协作**：任何调用方仍能以任何角色名义提交确认。这一点与 ADR-0002 相同，是同一取舍的延续。
- `MVP-004` 需从"提交者自由字符串"改为"角色成员槽位 + 历史快照"；`MVP-019`、M6 的待办归属随之明确。

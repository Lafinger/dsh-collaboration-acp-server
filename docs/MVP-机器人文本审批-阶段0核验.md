## 2. 已核实的平台通用事实

- [钉钉官方Node Stream SDK](<https://github.com/open-dingtalk/dingtalk-stream-sdk-nodejs>)已实际取得，核验时固定源码提交`e7fe301d9afdcc1d62d2b7ffeba6fe7768b6489c`。README说明需要在企业内部应用中添加机器人能力、选择Stream并发布；不是扫码应用天然具备机器人能力。
- [官方Stream概述](<https://open-dingtalk.github.io/developerpedia/docs/learn/stream/overview/>)明确：Stream用于钉钉调用开发者应用，应用调用钉钉仍用REST API；反向TLS连接不要求开发者新增公网IP、域名、入站端口或内网穿透。因此符合既定不扩公网边界，但不证明当前服务器已成功连过机器人。
- [官方机器人消息类型](<https://open-dingtalk.github.io/developerpedia/docs/learn/bot/message/>)实际示例包含：`chatbotCorpId`、`senderCorpId`、`robotCode`、`senderStaffId`、`conversationType`、`msgId`、`createAt`、`msgtype`及`text.content`。企业内部成员映射应核验`senderStaffId`与已有组织userId的一致性，不能照搬一个未经证实的回调`senderUserId`字段，更不能使用昵称或senderId猜账号。
- SDK外层Stream `headers.messageId`是传输ACK关联，内层`msgId`是机器人消息标识；后续需区分两者，在scope内使用稳定业务消息去重，不能只以一次连接的ACK标识代替。
- 固定SDK源码显示可限定CALLBACK主题、严格TLS、接收并发、重连及显式回调ACK。默认订阅可能包含所有EVENT，后续不得原样启用；需要只订阅机器人所需topic。实例化须关闭debug并拦截错误中的token/endpoint数据，不把默认SDK日志当成可直接用于生产的审计。
- 主动发送必须用官方主动私聊REST能力，不能依赖消息体的短期`sessionWebhook`。真实API权限／参数、长度／速率／错误分类、平台返回值及当前应用可调用性尚需核验，未据通用示例宣称通过。

官方主站若仅返回单页应用壳不算接口正文；第三方索引只能帮助定位，不代替当前应用权限或真人收发证据。

## 4. 当前缺口与所需证据

在**现有同一个企业内部应用**中，需要开发者后台的非秘密信息：

1. 机器人能力是否已启用且已发布，消息接收模式是否为Stream；
2. 该机器人实际`robotCode`，以及它确属当前同组织／同应用；
3. 企业内部机器人主动发送单聊所需权限是否已获授予；
4. 应用可见／可用范围是否包含A/B，不必扩大到全员；
5. 是否已有其他运行实例消费该机器人的Stream，避免新测试抢占或分流真实消息。

当前会话没有钉钉开发者管理端浏览器登录上下文；API文档和现有登录配置不能代替这些证据。可以提供机器人能力、权限及可见范围页面的**脱敏截图**，或非秘密的robotCode及相应确认；不要提供ClientSecret、accessToken、Cookie或扫码链接。不自行猜robotCode、不为测试向未知对象发消息。

若尚未开启，由用户先确认在原应用新增必要能力／授权的动作，再给出最小步骤；不另建新应用或群机器人、不扩大公开范围、不修改回调公网入口。本阶段不能用“先写个能跑的程序”绕过事先约定的平台门槛。

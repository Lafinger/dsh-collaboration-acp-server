## 第一轮答复

用户原话：

> Q1 我希望是通过钉钉机器人文本私聊通知和发送审批，被发送的人员直接回复该私聊消息即可。其他都按建议。

### 已确认

1. **文本私聊职责审批**：机器人用钉钉一对一文本消息通知并发送待决事项，收件成员直接在该机器人私聊中回复表达决定。本期不默认改成操作卡片、浏览器确认页或回DSH才能提交；具体回复如何绑定事项仍待决。
2. 依用户“其他都按建议”：钉钉为通知与必要决定入口；DSH负责资料上传、分析、方案登记／修订、主线任务执行和成果提交。本期不做机器人自然语言问答、群聊分析或自动任务执行。
3. 只做组织内机器人一对一私聊，不做项目群通知／群内审批。管理员不因此取得各职责代批权。
4. 原机器人“不代人决定”的业务含义保留：新目标是机器人承载本人决定，不是机器人或模型自动代批。现有默认回DSH决定的入口限制将由后续已批准设计明确变更，而非现在已开放。

### 尚不可当作已确认

- Q1用户明确选择文本私聊回复，但没有逐字确认是否排除钉钉原生审批实例；第二轮需要把“写回工作台而非钉钉官方审批流程”与回复事项绑定一起明确，避免偷设结论。
- 覆盖哪些正式决定（方案确认／本人成果完成评审／下游成果接收）。
- 回复协议：是否要求事项短号；多个项目、多待决、旧消息、无指向“同意”如何处理。
- 可靠的官方发件人身份与组织映射；消息引用能力、机器人发送／接收技术路径及应用能力需查官方文档，不靠推断。
- 已有DSH成员还是允许机器人开通新成员；新成员／空缺／职责变更及过期版本行为。
- 提醒种类和触发时机、发送失败／未知、重复事件、审计和回执、手机网络／服务外网入口边界等。

## 第四轮待确认边界

- 连接／网络：Stream出站接收＋官方API发个人消息，不新增公网入站；手机普通网络，DSH电脑原LAN/ZeroTier及扫码不变；应用能力不足停下处理，不自行换机器人或公开接口。
- 可靠性：事务内记业务与收件事件去重，提交后才反馈；发送已成功不重发，明确未发送的暂时失败有界退避，未知不盲重试，永久拒绝／权限不够停止；用户再次同动作短号查询返回已处理，重复回调不再执行决定；出站状态与正式决定分开，不许把平台ACK等同业务成功。
- 不通过／条件不满足：按原业务记拒绝/退回/拒收及原因；输入未接受时完成评审不能绕过，不自动接收依赖；机器人提示原因回DSH修改，不自动修订方案／新建任务／生成成果／模型重试。
